# 产品方向：软件做减法，智能体做加法

日期：2026-06-27

状态：封档基线

适用项目：`鑫泰铝业 数据中枢`

## 一句话方向

```text
数据中枢不要继续长成一个“大而全的软件系统”。
它要变成一个干净、可信、少入口的数据底座和大仪表盘。
智能体要在 NousResearch Hermes 基础上增强，负责在这个底座上查证、解释、追踪和推动闭环。
```

小白版：

```text
软件像仪表盘，负责把真实数据摆稳。
智能体像调度员，负责问、查、比、催、解释。
```

这里的“大仪表盘”不是再造一个新系统。

它指的是：

```text
管理端围绕 /manage 收口成一个大屏式工作台。
管理者在一个主界面里看结果、看来源、看异常、看 Hermes trace。
```

## 为什么要改方向

当前项目已经做了很多：

- 手机填报。
- 管理后台。
- 生产、能耗、报表、权限、钉钉、RAG。
- Hermes / 鑫泰铝业智能大脑骨架。
- 事实来源地图。
- 数据中枢减法审计。

问题不是“没有功能”。

真正的问题是：

```text
功能已经够多，但主链路还需要更可信。
历史入口、历史服务、历史计划太多，后续智能体容易读乱。
```

所以接下来不要先加页面，不要先扩领域，也不要先喊“全厂大脑完成”。

先做一件事：

```text
让 Hermes 能用真实来源回答 20 个现场自然语言问题，并留下证据。
```

## 软件要减什么

软件减法不是乱删代码。

软件减法是把用户真的用的路径留下，把历史绕路冻结，把重复加工合并。

### 1. 减入口

保留主入口：

- `/entry`：一线填报和专项录入。
- `/manage`：管理层、管理员、观察和追踪。

历史入口只做兼容：

- `/mobile/*` 继续跳到 `/entry/*`。
- `/review/*`、`/admin/*` 等旧入口继续收口到 `/manage/*`。

原则：

```text
新功能优先放进已有入口，不新开一个门户。
```

### 2. 减页面

不要每发现一个问题就新建一个页面。

优先把能力放进已有页面：

- 今日总览：放当天关键结果和来源状态。
- 实时运行：放现场变化和卡点。
- 生产分析：放趋势、口径和对比。
- 异常中心：放冲突、缺失、待确认。
- AI 控制：放 Hermes 运行、证据、任务和灰度。

页面最终要朝“大仪表盘 + 少数必要子页”收口。

大仪表盘负责：

- 看全局。
- 看关键指标。
- 看来源状态。
- 看异常和冲突。
- 看 Hermes trace。

### 3. 减重复服务

有些服务是历史阶段长出来的加工层。

不要马上删。

先按 [数据中枢冻结与候选删除登记表](./datahub-deprecation-register.md) 做三步：

1. 标记：protect、freeze、merge、candidate_delete。
2. 观察：7 到 14 天。
3. 验证：没有生产依赖，再合并或删除。

### 4. 减假完成

以下情况不能写成“已完成”：

- 只有 mock 数据。
- 只有骨架测试，没有真实 smoke。
- 只有 RAG 命中，没有事实来源。
- 只有页面能打开，没有业务链路验证。
- 只有模型回答，没有 trace_id 和来源。

## 智能体要加什么

智能体加法不是加更多聊天窗口。

智能体应该加在“人最累、最容易错、最需要追溯”的地方。

智能体方向必须建立在 NousResearch Hermes 的模型和推理能力基础上。

项目里的 Hermes 不是重新发明一个模型，而是在这个基础上加业务能力：

- 懂鑫泰铝业的指标口径。
- 会查 MES/WMS 只读来源。
- 会查 DailyFactBundle。
- 会查钉钉专项证据。
- 会留下 trace。
- 会把缺失和冲突推进成任务。

### 1. 加理解

用户不需要记字段名。

用户可以问：

```text
今天成品入库多少？
彩涂车间今天电耗为什么高？
今天日报里哪个数字最不可信？
```

Hermes 要把这些话转成指标、日期、车间、来源计划。

### 2. 加证据

每个关键回答都要能说清：

- 数字是多少。
- 日期范围是什么。
- 来源是哪张表、哪个接口、哪个文件或哪条钉钉证据。
- 来源优先级为什么这样排。
- `trace_id` 是什么，方便回查。

涉及生产、库存、在制、入库、工序、包装等问题时，还要确认 MES 数据库读取链路：

```text
MES 数据库只读连接
  -> MES/WMS adapter
  -> 数据中枢投影或 DailyFactBundle
  -> Hermes 来源计划
  -> Hermes 回答和 trace
```

链路不通时，Hermes 要说“读取链路未通”，不能改用猜测数字。

### 3. 加冲突判断

同一个指标可能有多个来源。

比如“产量”可能来自：

- DailyFactBundle。
- MES/WMS 只读投影。
- 专项责任人钉钉证据。
- 历史日报。

Hermes 要能说明：

```text
我采用 A，因为它优先级更高。
我不采用 B，因为它缺少时间范围。
我把 C 标记为待确认，因为它和 A 差异过大。
```

### 4. 加闭环

回答不是终点。

如果证据缺失，Hermes 要生成下一步动作：

- 通知专项责任人补证据。
- 生成数据质量任务。
- 标记事实来源缺口。
- 把本次问题写入 smoke 集。

## 接下来 30 天的主线

只抓一条主线：

```text
Hermes 真实证据闭环。
```

验收重点：

- 20 个自然语言问题。
- 每个问题都有真实来源计划。
- 能取到值就返回值。
- 取不到值就明确说缺什么。
- 有冲突就说明冲突。
- 每次回答都有 `trace_id`。
- 管理端能看到证据和状态。

## 不做什么

下一阶段明确不做：

- 不新建一套大而全驾驶舱。
- 不把 `数据中枢` 改叫 `MES`。
- 不新增没有验收链路的 AI 设想。
- 不为了好看堆解释文案。
- 不删除原始证据、审计日志、Hermes 依赖链。
- 不让 RAG 替代实时生产数字来源。
- 不绕过 MES 数据库只读链路直接编生产答案。
- 不把没有真实 smoke 的能力写成上线完成。

## 判断一个需求该不该做

用 5 个问题判断：

1. 它能不能帮助 20 个真实问题更可信？
2. 它能不能减少一个旧入口、旧页面或旧加工层？
3. 它能不能让来源、冲突、缺失更清楚？
4. 它有没有明确验收命令或真实证据？
5. 它是不是可以放进已有页面，而不是新开一套？

如果 5 个问题大多回答“不能”，先不做。
