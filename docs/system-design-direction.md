# 系统与界面设计方向：让数据中枢变小，让智能体变强

日期：2026-06-27

状态：封档基线 / DESIGN 方向文档

适用项目：`鑫泰铝业 数据中枢`

## 1. 设计目标

```text
页面更少，路径更清楚。
数据更可信，来源更可查。
软件收口成大仪表盘，智能体基于 NousResearch Hermes 增强，但不把软件越堆越重。
```

小白版：

```text
用户不要在一堆入口里找功能。
用户只看该看的页面。
有疑问时，让 Hermes 把来源和下一步找出来。
```

## 2. 系统分层

当前系统按 5 层理解：

```text
用户入口
  -> /entry 和 /manage

业务页面
  -> 大仪表盘、今日、实时、生产、异常、AI 控制

事实层
  -> MES 数据库只读链路
  -> DailyFactBundle
  -> 外接只读投影
  -> 钉钉证据
  -> 历史日报

智能体层
  -> 基于 NousResearch Hermes 增强的 Hermes 理解、查证、判断、留痕、生成任务

治理层
  -> 权限、审计、trace、减法登记、灰度门禁
```

设计重点不是再加第六层。

设计重点是把这五层打通。

数据中枢在事实链路里的定位：

数据中枢负责读取、投影、缓存、展示和审计。

它不是最高事实源。

当钉钉群事实或外接只读数据库事实与数据中枢投影冲突时，大仪表盘和 Hermes trace 应显示冲突，而不是用数据中枢投影覆盖上游事实。

## 3. 路由设计

### 3.1 主入口

只保护两类主入口：

| 入口 | 给谁用 | 作用 |
|---|---|---|
| `/entry` | 一线人员、专项责任人 | 填报、补证据、处理专项任务。 |
| `/manage` | 管理层、管理员、观察人员 | 看结果、看来源、看异常、看智能体运行。 |

`/manage` 的长期形态是大仪表盘。

它不是一个只展示 KPI 的大屏，而是一个工作台：

- 左边或顶部看全局状态。
- 中间看核心指标。
- 旁边看来源、异常和冲突。
- 需要时能进入 Hermes trace。

### 3.2 历史入口

历史入口不要继续长业务。

| 旧入口 | 处理 |
|---|---|
| `/mobile/*` | 保留兼容，跳到 `/entry/*`。 |
| `/review/*` | 保留兼容，跳到 `/manage/*`。 |
| `/admin/*` | 保留兼容，收口到 `/manage/*`。 |
| `/dashboard/*` | 不再作为新功能首选入口。 |

## 4. 页面设计

### 4.1 `/entry`

`/entry` 是一线工作台。

它要做到：

- 少字。
- 少选择。
- 任务明确。
- 能补证据。
- 能看到提交状态。

不做：

- 不放管理分析。
- 不放大段说明。
- 不堆复杂筛选。

### 4.2 `/manage/today`

今日总览是管理层第一屏。

它要回答：

- 今天核心数字是什么。
- 哪些数字已确认。
- 哪些数字候选。
- 哪些数字缺失。
- 哪些数字冲突。

每个关键数字应该能看到来源状态。

### 4.3 `/manage/live`

实时运行页看现场变化。

它要回答：

- 当前哪里在生产。
- 哪个环节卡住。
- 哪些数据刚刚变化。
- 哪些变化需要确认。

不要把实时页做成第二个日报页。

### 4.4 `/manage/production`

生产分析页看趋势和口径。

它要回答：

- 产量怎么变。
- 入库怎么变。
- 在制怎么变。
- 口径有没有混淆。

关键设计：

```text
产量、入库、投料、在制不能混成一个“生产数”。
```

### 4.5 `/manage/alerts`

异常中心看缺失和冲突。

它要回答：

- 哪些指标缺来源。
- 哪些来源互相冲突。
- 哪些需要专项责任人确认。
- 哪些已经处理。

### 4.6 `/manage/ai-control`

AI 控制页看 Hermes。

它要回答：

- Hermes 最近回答了什么。
- 查了哪些来源。
- 哪些 trace 成功。
- 哪些 trace 失败。
- 哪些 smoke 没过。

## 5. 数据流设计

目标数据流：

```text
MES 数据库 / 外部生产系统 / 钉钉 / 手工填报 / 历史日报
  -> 事实采集和投影
  -> DailyFactBundle 或对应事实表
  -> Hermes 来源计划
  -> Hermes 真实取数
  -> 回答、trace、任务、页面状态
```

这个流里每一步都要能回查。

MES 数据库读取链路必须单独看成一条红线：

```text
MES 数据库只读连接
  -> MES/WMS adapter
  -> 数据中枢投影
  -> DailyFactBundle 或事实表
  -> Hermes 证据引用
  -> 页面来源状态
```

只要这个链路不通，生产事实类回答就不能宣称 confirmed。

不能出现：

```text
页面上有数字，但没人知道从哪里来。
Hermes 能回答，但没人知道它查了什么。
```

## 6. 界面增强方式

界面增强优先用状态和证据，不靠长说明。

建议组件：

| 场景 | 设计 |
|---|---|
| 已确认数字 | 显示 confirmed 状态和来源入口。 |
| 候选数字 | 显示 candidate 状态和待确认来源。 |
| 缺失数字 | 显示 missing 状态和补证据动作。 |
| 冲突数字 | 显示 conflict 状态和冲突来源。 |
| Hermes 回答 | 显示 trace_id、来源、下一步。 |

注意：

- 不新增解释型大段文案。
- 不用页面文字教用户怎么用系统。
- 不新增 `description`、`explanation`、`helperText`、`tooltip`、`note`、`rationale` 这类 schema 或组件 prop。
- 图标、状态、来源入口要比说明文字更重要。

## 7. 代码设计

### 7.1 保留核心链路

这些链路优先保护：

- MES 数据库只读读取链路。
- DailyFactBundle。
- Hermes 事实来源地图。
- Hermes / Factory Brain。
- 钉钉证据。
- MES/WMS 只读投影。
- 权限和审计。
- trace 和 agent_runs。

### 7.2 收口重复加工

重复报表加工、历史 dashboard builder、旧 overview builder 不直接删。

先做：

1. 标记。
2. 观察。
3. 验证依赖。
4. 合并。
5. 最后才删除。

### 7.3 不新增大抽象

除非一个抽象能减少真实重复，否则不要新增。

判断标准：

```text
如果只有一个地方用，就先不要抽象。
如果只是为了以后可能用，也先不要抽象。
```

## 8. 验收设计

每次设计或代码变更，都要能回答：

| 问题 | 说明 |
|---|---|
| 少了什么？ | 少入口、少页面、少重复服务，还是少文档噪音。 |
| 强了什么？ | Hermes 查证、来源、trace、冲突判断有没有变强。 |
| 怎么验证？ | 写出命令、页面路径或真实 smoke。 |
| 怎么回滚？ | 尤其是冻结、合并、删除类变更。 |

## 9. 完成标准

本设计方向落地后，用户应该感觉到：

```text
入口更少了。
页面更清楚了。
数字更能追溯了。
Hermes 不只是聊天，而是在帮我查证和推进事情。
```
