# DESIGN：Hermes root_owner 生产私聊真实证据闭环 MVP

日期：2026-06-27

状态：待评审

适用项目：`鑫泰铝业 数据中枢`

## 0. 一句话结论

本期要做的不是再加一个页面，也不是再造一个数据系统。

本期要把 Hermes 做成一个能在真实钉钉私聊里回答老板问题的智能体：

```text
root_owner 在钉钉私聊里问一句话
Hermes 先查钉钉群文件和聊天内容
再按业务领域查外接只读数据库
最后才查数据中枢投影、缓存、日报包和历史记录
回答必须能留下 trace
```

小白版：

```text
先找现场和负责人在钉钉里确认过的口径。
再找源头业务数据库。
数据中枢只负责搬运、整理、展示和留证据。
```

## 1. 目标

### 1.1 产品目标

让 `数据中枢` 继续做减法：

- 不再为了每个问题新开页面。
- 不再把缓存、投影、日报包误当成最高事实。
- 管理端继续围绕 `/manage` 做大仪表盘和 trace 查看。

### 1.2 智能体目标

让 Hermes 在 NousResearch Hermes 基础上增强：

- 能听懂 root_owner 的自然语言问题。
- 能查真实事实源。
- 能在事实冲突时按优先级选择。
- 能估算，但必须说明依据和置信度。
- 能把回答、证据、冲突、失败写入 trace。

### 1.3 验收目标

本期验收只看一个核心闭环：

```text
真实 root_owner 钉钉私聊
  -> Hermes 理解问题
  -> 查最高优先级事实源
  -> 生成一段自然语言回答
  -> 真实发回钉钉私聊
  -> 后台留下 trace、外部通讯日志和失败重试记录
```

## 2. 非目标

本期不做：

- 不重做整套管理后台。
- 不新建第二个数据中枢。
- 不把 RAG 当实时数字事实源。
- 不让普通用户触发真实私聊回复。
- 不把没有依据的数字写成已确认事实。
- 不为了“看起来智能”增加一堆解释页面。

## 3. 核心领域规则

### 3.1 最高事实源：钉钉群文件和群聊天内容

钉钉群内文件和聊天内容是最高优先级事实源。

这里的“钉钉内容”包括：

- 群文件。
- 群聊天记录。
- 老板确认口径。
- 生产负责人回复。
- 专项责任人补充说明。
- 异常说明。
- 临时安排。
- 制度文件和口径文件。

规则：

```text
如果钉钉群内容和数据库数字冲突，
Hermes 优先采用钉钉内容。
```

原因：

```text
工厂真实运行里，很多事实不是先进入数据库。
现场确认、临时调整、异常说明、负责人定口径，往往先发生在钉钉。
```

### 3.2 外接只读数据库：按业务领域成为事实本身

外接只读数据库不是数据中枢的下级来源。

它在自己负责的业务领域里就是事实本身。

例如：

- MES 只读库负责生产域事实。
- 未来能耗只读库负责能耗域事实。
- 未来其他外接只读库负责各自业务域事实。

规则：

```text
外接只读库能直接回答的字段，
Hermes 不能优先采用数据中枢缓存值。
```

### 3.3 数据中枢：读取、投影、缓存、展示、审计层

数据中枢不是最高事实源。

它负责：

- 读取外部来源。
- 做本地投影。
- 做缓存。
- 做大仪表盘展示。
- 保存 trace。
- 保存外部通讯日志。
- 标记缺失和冲突。
- 帮人看到哪里需要补证据。

它不能：

- 用自己的缓存压过钉钉群事实。
- 用自己的投影压过外接只读库。
- 把 RAG 命中内容包装成实时数字事实。

## 4. 事实优先级

Hermes 查证据时按这个顺序：

| 优先级 | 来源 | 用途 | 冲突时怎么处理 |
|---:|---|---|---|
| 1 | 钉钉群文件和群聊天内容 | 现场口径、负责人确认、异常说明、临时安排、制度文件 | 优先采用 |
| 2 | 外接只读数据库 | MES 生产事实、未来能耗事实、其他业务域事实 | 在本业务域内优先于数据中枢 |
| 3 | 数据中枢本地投影 | 为查询和展示准备的本地副本 | 只能作为投影和加速层 |
| 4 | DailyFactBundle / 历史日报 | 日报汇总、历史快照、回溯 | 可参考，但不能压过更高事实源 |
| 5 | 人工填报 | 补充缺口、临时登记 | 需要看是否被钉钉或负责人确认 |
| 6 | RAG 知识库 | 解释原因、查制度、辅助分析 | 不能单独当实时数字事实 |

小白版：

```text
钉钉是现场和组织口径。
外接库是业务源头数字。
数据中枢是搬运和展示。
日报是整理后的结果。
RAG 是解释材料，不是实时数字源头。
```

## 5. 问题范围

root_owner 可以自由问：

- 生产。
- 库存。
- 能耗。
- 异常。
- 日报是否能生成。
- 哪些数字缺来源。
- 哪些来源互相冲突。
- 某个现象可能是什么原因。

本期不要求固定只能问 20 个问题。

但验收 smoke 要覆盖四类问题：

| 类型 | 示例 |
|---|---|
| 事实 | 今天全厂产量是多少？ |
| 估算 | 今天吨电耗大概是多少？置信度多高？ |
| 缺失 | 今天日报还缺哪些数字？ |
| 异常 | 产量和入库为什么对不上？ |

## 6. 消息识别规则

消息识别不能设计得太硬。

root_owner 的真实私聊可能是口语、短句、错别字、省略句、追问，甚至只有一句“今天咋样”。

Hermes 不能只靠固定关键词、固定句式或固定 20 个问题来识别。

### 6.1 识别原则

允许：

- 模糊匹配。
- 语义匹配。
- 上下文追问。
- 业务别名。
- 口语表达。
- 错别字容错。
- 时间省略，比如默认今天。

不允许：

- 只有完全匹配关键词才回答。
- 只支持预设问题。
- 识别不出来就直接失败。
- 把不确定的问题硬编成确定答案。

### 6.2 识别不确定时

如果 Hermes 不确定用户到底问什么，要先做降级处理：

1. 能判断大概业务域时，先给最佳努力回答，并说明不确定点。
2. 不能判断具体指标时，反问一个最短澄清问题。
3. 不能查到事实源时，说明缺哪个来源，而不是报错。
4. 原始消息必须写入 trace，方便后续优化识别规则。

小白版：

```text
老板怎么问都应该尽量接住。
听不准就问一句，不要直接说识别失败。
```

## 7. 回答规则

### 7.1 回复形态

Hermes 回复 root_owner 时用一段自然语言。

不强制分成很多小标题。

但这段话里必须自然包含：

- 结论。
- 关键数字。
- 时间范围。
- 来源。
- 是否估算。
- 置信度。
- 有冲突时说明采用了哪个来源。

### 7.2 数字估算

Hermes 可以估算数字。

但必须满足：

```text
有依据才估算。
估算必须写置信度。
估算必须写为什么这么估。
```

事实数字只能来自：

- 钉钉群文件和群聊天内容。
- 外接只读数据库。
- 数据中枢投影。
- DailyFactBundle。
- 历史日报。
- 人工填报。

原因分析可以参考 RAG。

### 7.3 缺失处理

查不到时不能编。

回答应该说明：

- 缺哪个事实源。
- 缺哪个字段。
- 缺哪个日期或车间。
- 是否外接库不可达。
- 是否钉钉证据未同步。
- 下一步该由谁补。

## 8. root_owner 钉钉私聊

### 8.1 触发入口

本期入口是：

```text
root_owner 钉钉私聊 Hermes
```

不是测试群，不是业务大群，也不是纯 API 验收。

### 8.2 身份判断

第一版只看钉钉 `user_id` 是否在 root_owner 环境变量白名单里。

```text
DINGTALK_ROOT_OWNER_USER_IDS=xxx,yyy
```

只有命中 root_owner 的私聊才允许触发真实回复。

### 8.3 真实发送

本期接真实钉钉私聊发送。

不再只停留在模拟响应。

发送失败时要写：

- 外部通讯日志。
- outbox 重试记录。
- 管理员可查的失败原因。

## 9. 查询链路设计

### 9.1 总链路

```text
root_owner 钉钉私聊
  -> Hermes 接收消息
  -> 校验 root_owner 身份
  -> 理解问题属于哪个业务域
  -> 先查钉钉群文件和聊天内容
  -> 再查该业务域外接只读数据库
  -> 再查数据中枢投影、日报包、历史记录、人工填报
  -> 需要解释原因时查 RAG
  -> 生成一段自然语言回答
  -> 发回 root_owner 钉钉私聊
  -> 写 trace、通讯日志、outbox 状态
```

### 9.2 钉钉事实读取

Hermes 需要能把钉钉群文件和群聊天内容纳入事实检索。

最小可用能力：

- 能按日期检索。
- 能按关键词检索。
- 能按群或业务主题检索。
- 能区分聊天内容、文件内容和负责人确认。
- 能把命中的钉钉证据写进 trace。

### 9.3 外接只读数据库注册表

外接只读数据库统一进入后端注册表。

第一版先做配置和健康检查，不做复杂前端配置页。

注册表至少要表达：

| 字段 | 含义 |
|---|---|
| `source_key` | 来源标识，比如 `mes_readonly`、`energy_readonly` |
| `domain` | 负责的业务域，比如生产、能耗 |
| `priority` | 在该业务域内的优先级 |
| `readonly` | 必须为只读 |
| `health_status` | 当前是否可读 |
| `last_success_at` | 最近一次成功读取时间 |
| `failure_reason` | 最近失败原因 |

### 9.4 MES 读取链路

涉及生产域时，必须保证 MES 数据库只读链路通畅。

链路：

```text
MES 只读数据库
  -> MES read adapter
  -> 数据中枢本地投影或查询结果
  -> Hermes evidence tool
  -> trace
  -> root_owner 私聊回答
```

验收时不能只看模型回复。

必须证明：

- 只读连接成功。
- 能查到目标业务字段。
- 查询结果进入 trace。
- 回答引用了这个来源，或说明被更高优先级钉钉内容覆盖。

### 9.5 未来能耗库

未来能耗库按同一套注册表接入。

本期只要求设计上留出：

- `energy_readonly` 来源类型。
- 能耗域优先级。
- 健康检查。
- 查询失败 trace。

不要求本期真正接入能耗库。

## 10. 冲突处理

冲突不是错误。

冲突是必须被看见的事实。

### 10.1 钉钉和数据库冲突

规则：

```text
优先采用钉钉群文件或群聊天内容。
```

回答里可以简单说明：

```text
我按钉钉里负责人确认的口径回答；MES 只读库当前数字不同，已记录为来源冲突。
```

trace 里必须保存：

- 钉钉证据。
- 外接库数字。
- 差异点。
- 采用钉钉的原因。
- 是否需要人工复核。

### 10.2 外接库和数据中枢投影冲突

规则：

```text
在外接库负责的业务域内，优先采用外接只读库。
```

数据中枢投影只是本地副本。

如果本地投影不同，说明同步、转换或口径可能有问题。

### 10.3 DailyFactBundle 和更高来源冲突

DailyFactBundle 是汇总结果，不是最高事实。

如果它和钉钉或外接库冲突：

- 回答采用更高事实源。
- trace 记录 DailyFactBundle 差异。
- 生成数据质量任务或待复核项。

## 11. Trace 和日志

每次真实私聊回答都必须留下 trace。

trace 至少包括：

- `trace_id`。
- root_owner 钉钉 `user_id`。
- 原始问题。
- 识别出的业务域。
- 查询过的来源。
- 命中的钉钉证据。
- 命中的外接库结果。
- 数据中枢投影结果。
- 是否估算。
- 置信度。
- 冲突记录。
- 最终回答。
- 钉钉发送状态。

外部通讯日志至少包括：

- 发送目标。
- 发送内容摘要。
- 发送时间。
- 成功或失败。
- 失败原因。
- 重试次数。

## 12. 管理端边界

本期不新建新页面。

只要求把 trace 和日志写好。

后续管理端大仪表盘可以在 `/manage` 里读取这些 trace 和日志。

本期可以只保证：

- 后台可查 trace。
- 后台可查通讯日志。
- 后台可查 outbox 重试状态。
- 不为了展示新建一套门户。

## 13. 验收标准

### 13.1 生产 smoke

必须做真实生产 smoke。

建议 5 到 10 个问题，覆盖：

- 事实。
- 估算。
- 缺失。
- 异常。

每个问题都要证明：

- root_owner 身份命中。
- Hermes 收到真实私聊。
- Hermes 查询了事实源。
- 真实回复发送成功，或失败进入 outbox。
- trace 可回查。

### 13.2 必须通过

| 验收项 | 通过标准 |
|---|---|
| root_owner 私聊 | 只有 root_owner 环境变量白名单里的钉钉用户能触发真实回复 |
| 钉钉事实优先 | 钉钉群文件或聊天内容与数据库冲突时，采用钉钉内容 |
| 外接库领域优先 | MES 等外接库在自己业务域内高于数据中枢投影 |
| MES 只读链路 | 生产域问题能证明 MES 只读读取、查询结果、trace 全链路通畅 |
| 估算 | 估算值带依据和置信度 |
| 缺失 | 查不到时说明缺哪个来源，不编数字 |
| 冲突 | 冲突被记录到 trace，不被悄悄抹平 |
| 钉钉发送 | 成功写通讯日志，失败进入 outbox 重试 |
| 管理端边界 | 不新建大后台，只写 trace 和日志供 `/manage` 后续读取 |
| 识别容错 | 口语、错别字、省略句和追问不能直接识别失败，要最佳努力回答或最短澄清 |

### 13.3 不能算通过

- 只跑 API，不接真实钉钉私聊。
- 只看模型回答，不查真实来源。
- 数据库和钉钉冲突时仍然优先采用数据库。
- 数据中枢缓存压过外接只读库。
- RAG 命中就直接当实时数字事实。
- 没有 trace。
- 没有外部通讯日志。
- 没有 outbox 重试。
- 只能识别固定关键词或固定问题。

## 14. 推荐实施切片

### 切片 1：事实源优先级和 trace 模型

完成：

- 明确钉钉事实最高优先级。
- 明确外接库按业务域优先。
- 调整 Hermes evidence planner。
- trace 能记录采用和不采用的来源。

### 切片 2：root_owner 私聊真实入口

完成：

- 钉钉私聊接收。
- root_owner 环境变量白名单。
- 真实回复发送。
- 外部通讯日志。
- outbox 重试。

### 切片 3：消息识别容错

完成：

- root_owner 口语问题可识别。
- 错别字、省略句、追问可降级处理。
- 不确定时能最佳努力回答或最短澄清。
- 原始消息和识别结果进入 trace。

### 切片 4：钉钉群内容事实检索

完成：

- 群聊天内容可检索。
- 群文件内容可检索。
- 命中结果可写 trace。
- 与数据库冲突时优先采用钉钉。

### 切片 5：外接只读库注册表

完成：

- MES 只读库注册。
- 健康检查。
- 生产域查询链路证明。
- 预留未来能耗库配置位。

### 切片 6：生产 smoke

完成：

- 5 到 10 个真实私聊问题。
- 覆盖事实、估算、缺失、异常。
- 每个问题有 trace。
- 每个问题有发送日志。
