# 07:30 预报版、09:30 正式版与填报端角色清理设计

日期：2026-06-17

## 1. 目标

把填报端从“人工统计角色很多”收口成“人只补机器拿不到的事实”。

每天输出分两段：

1. `07:30` 自动生成生产预报版。
2. `09:30` 自动生成正式日报版，并尽量对齐 `D:\输出skill` 的日报内容和核对记录。

小白版理解：早上 `07:30` 先把机器已经有的生产数字发出来；`09:30` 等人工必须确认的补充项到齐后，再发最终版。

## 2. 已确认事实

### 2.1 项目现状

系统当前主线是：

- `/entry`：岗位手机填报端。
- `/manage`：管理审阅和驾驶舱。
- Agent：自动校验、汇总、催报、推送。
- `D:\输出skill`：现有人工/脚本日报输出参考目录。

生产业务日是早上 `07:30` 到次日 `07:30`。

内勤/专项每日一录当前是早上 `09:30` 口径。

当前调度器里自动日报任务是每天 `08:00`，不是 `07:30`。

### 2.2 输出 skill 现实节奏

最近几天 `D:\输出skill` 的日报正文和核对记录多在 `09:13` 到 `10:08` 左右生成。

原因不是单纯脚本慢，而是部分来源文件本身晚于 `07:30` 才到齐，例如能源、成品率、耗材、专项补充和人工确认项。

### 2.3 外部数据源现实

MES SQL Server 已只读连通。核心表能覆盖大量生产事实：

- 工序流转。
- 车间、工序、设备。
- 上机、下机、结束时间。
- 包装和入库。
- 合同明细。
- 在制相关线索。

以 `2026-06-16 07:30` 到 `2026-06-17 07:30` 生产窗口只读核验，MES 中大多数生产、入库、合同数据在 `07:30` 前已经可读。

能源 MySQL 当前端口可达，但 MySQL 握手和最轻查询都会超时断开。设计上不能把它当作 `07:30` 稳定实时源，必须先做本地影子同步和超时降级。

## 3. 推荐方案

采用“双阶段日报闭环”。

### 3.1 07:30 生产预报版

`07:30` 只使用稳定事实源：

- MES 工序产量。
- MES 包装和入库参考。
- MES 合同和在制线索。
- 本地已同步能耗影子表。
- 前一天已经确认的人工补充项。

如果某个字段还没到齐，预报版要明确标记：

- `待补`
- `未同步`
- `能源库不可用`
- `内勤 09:30 后确认`

预报版不允许用大模型编数字，也不允许用上次值冒充正式事实。

### 3.2 09:30 正式日报版

`09:30` 合并这些后补来源：

- 内勤/专项每日一录。
- 成品库入库、寄存、发运确认。
- 能源、电工或总电工确认。
- 成品率、质量门禁、异常处理结论。
- 回收、大修、耗材等专项数据。
- 输出 skill 口径对齐结果和差异说明。

正式版用于管理层日报、钉钉推送、日报归档和对齐审计。

### 3.3 不采用的方案

不采用 `07:30` 强行完整日报。

原因：这样会把缺失能源、成品率、耗材、专项补充的字段硬填满，容易把估算当事实，最终造成日报和现场信任问题。

## 4. 角色保留设计

保留原则：只保留真实数据链路需要的人。

### 4.1 填报端保留角色

| 角色 | 保留原因 |
|---|---|
| `machine_operator` 主操/机台账号 | 补 MES 缺口、卷级确认、异常说明、现场照片 |
| `energy_stat` 电工 | 能源库稳定前负责电、气、水兜底 |
| `storage_owner` 成品库 | 入库、寄存、发运口径和 MES 包装产量不是同一个数 |
| `quality_owner` 质检 | 质量门禁、异常处理结论 |
| `planning_owner` 计划 | 合同、计划类人工确认 |
| `energy_chief` 总电工 | 全厂能耗确认 |
| `recovery_owner` 回收 | 回收日报专项 |
| `overhaul_owner` 大修 | 磨辊、大修能耗等专项 |
| `shipment_outflow_owner` 发运/剪切 | 发运、园区剪切专项 |

### 4.2 管理端保留角色

| 角色 | 保留原因 |
|---|---|
| `workshop_director` 车间主任 | 看本车间结果、处理异常，不做人工统计 |
| `manager` / `factory_director` 管理层 | 看聚合结果、日报和风险 |
| `admin` 管理员 | 账号、主数据、通道、配置和门禁 |

### 4.3 Agent 保留角色

| Agent | 保留原因 |
|---|---|
| `validator` | 自动校验、退回、自动确认 |
| `aggregator` | 自动汇总日报 |
| `reporter` | 自动触达管理层 |
| `reminder` | 自动催报 |

## 5. 角色删除设计

用户已确认：不做历史兼容。确认不影响数据链路后，旧角色直接删除，不只是停用。

### 5.1 可直接进入删除的旧角色

最近 7 天线上只读审计没有发现真实使用：

- `statistician`
- `stat`
- `reviewer`
- `mobile_user`
- `team_leader`
- `deputy_leader`
- `shift_leader`
- `contracts`
- `inventory_keeper`
- `utility_manager`

`qc` 只有停用账号，最后登录在 2026-04-30，最近 7 天没有使用，可进入删除。

### 5.2 可删除的旧二维码

`OP` 虚拟二维码已有 5 个记录，均停用、未绑定用户。

未发现 `BZ` 活跃记录。

结论：`BZ`、`OP` 旧虚拟二维码可以进入删除。

### 5.3 暂不能直接删除的旧角色

`consumable_stat` 最近 7 天仍在真实使用：

- 有 6 个用户最近登录。
- 有 30 次扫码登录。
- 有 20 条最近 `work_order_entries` 写入。
- 2026-06-17 早上仍有写入。
- 催报记录中也仍引用该角色。

结论：`consumable_stat` 不能直接删。必须先迁移到明确 owner 角色，再删除旧角色。

### 5.4 consumable_stat 迁移原则

迁移时不要只改角色名，要看它实际填的字段属于哪类事实：

- 成品库、入库、寄存：迁到 `storage_owner`。
- 发运、园区剪切：迁到 `shipment_outflow_owner`。
- 能源类：迁到 `energy_chief` 或 `energy_stat`。
- 质量类：迁到 `quality_owner`。
- 计划/合同类：迁到 `planning_owner`。
- 回收类：迁到 `recovery_owner`。
- 大修类：迁到 `overhaul_owner`。

迁移完成并连续几天确认无使用后，再删除 `consumable_stat`。

## 6. 删除前门禁

删除旧角色前必须通过只读审计：

1. 最近 7 天无登录。
2. 最近 7 天无填报写入。
3. 最近 7 天无审计动作。
4. 最近 7 天无催报引用。
5. 无活跃二维码绑定。
6. 无前端入口仍依赖。
7. 无后端权限判断仍依赖。
8. 无测试仍把旧角色当正式角色。

如果历史业务记录仍通过外键引用旧账号，不能直接删业务数据。处理方式是：

- 先迁移到新 owner 账号；或
- 改为保留审计归档身份，但不再作为可登录用户和业务角色。

这里的原则是：可以删除旧角色入口和权限，但不能破坏历史数据追溯。

## 7. 数据流设计

### 7.1 07:30 预报版数据流

```text
生产业务日闭合
  -> 只读同步 MES
  -> 读取本地投影表
  -> 生成预报版日报
  -> 标记缺口字段
  -> 管理端展示 / 可推送摘要
```

### 7.2 09:30 正式版数据流

```text
专项补充到齐
  -> 合并 owner daily
  -> 合并能源和质量确认
  -> 跑输出 skill 对齐
  -> 生成正式日报
  -> 生成核对记录和差异说明
  -> 推送 / 归档 / 审计
```

## 8. 前端设计

`/entry` 保持极简，不增加统计员式页面。

填报端只显示当前角色真正要填的内容：

- 主操：卷级确认、异常、照片。
- 电工：能耗兜底。
- owner 角色：每日一录专项字段。

`/manage/today` 和日报相关页面要明确区分：

- `预报版`
- `正式版`
- `待补字段`
- `数据来源`
- `和输出 skill 差异`

页面不能只写“今日”，要写清楚生产业务日口径。

## 9. 后端设计

需要新增或调整的能力：

1. 调度任务支持 `07:30` 预报版。
2. 调度任务支持 `09:30` 正式版。
3. 日报模型或 payload 能区分 `forecast` 和 `final`。
4. 输出 skill 对齐服务接入正式版生成流程。
5. 旧角色删除前提供只读审计命令。
6. `consumable_stat` 迁移完成前保留，但标记为待迁移角色。
7. 权限、字段、二维码、前端菜单、测试统一移除已删除旧角色。

## 10. 测试设计

后端测试：

- `07:30` 预报版在缺能源库时仍能生成。
- 预报版缺字段必须标记待补，不能填假数。
- `09:30` 正式版能合并 owner daily。
- 输出 skill 对齐差异能进入正式版结果。
- 旧角色无最近使用时可进入删除候选。
- `consumable_stat` 有最近写入时不能进入删除候选。
- 删除旧角色后 `/entry`、日报、催报、审计仍可用。

前端测试：

- 日报页能区分预报版和正式版。
- 待补字段能显示。
- 已删除角色不再出现在用户管理、二维码、填报入口、导航和测试文案中。
- `consumable_stat` 迁移前不被错误隐藏。

## 11. 验收标准

1. 每天 `07:30` 能自动产出预报版。
2. 每天 `09:30` 能自动产出正式版。
3. 正式版能给出和 `D:\输出skill` 的差异说明。
4. 已确认无使用的旧角色被删除，不保留兼容入口。
5. `consumable_stat` 先迁移再删除，不能断掉真实填报。
6. 删除后主链路仍可用：`/entry`、`/manage`、日报、催报、权限、审计。
7. 最终输出不包含数据库口令、钉钉密钥或其他敏感配置。

## 12. 当前决策

已确认：

- 采用 `07:30` 预报版 + `09:30` 正式版。
- 不做旧角色历史兼容。
- 最近几天没人使用的旧角色直接拆。
- `consumable_stat` 因为最近仍在使用，先迁移职责，再删除。

下一步应进入实施计划：先做只读审计命令和角色迁移门禁，再改日报双阶段调度，最后拆旧角色代码和前端入口。
