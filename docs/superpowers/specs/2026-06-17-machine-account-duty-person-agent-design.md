# 2026-06-17 机台账号、当班人员责任与 AI Agent 设计 Spec

## 1. 背景

`鑫泰铝业 数据中枢` 现在的现场填报入口主要依赖机台账号。机台账号稳定，二维码也稳定，适合代表“哪台机、哪个车间、哪个工序”。

但真实人员会轮班、换岗、代班。把钉钉人员直接同步成系统业务账号，或者把某个人长期绑定到某台机，都会造成责任错乱。

因此本设计的核心原则是：

- 机台账号继续作为稳定填报入口。
- 钉钉人员不直接变成业务账号。
- 人员只绑定到“某个业务日、某个班次、某台机、某次填报”。
- AI Agent 只能查系统事实、规则和 RAG 资料，再组织语言，不能自己编数字。

## 2. 当前代码事实

当前系统已有以下基础：

- `users` 表已有机台账号、管理员账号、移动端账号等统一账号字段。
- `users.dingtalk_user_id` 和 `users.dingtalk_union_id` 已存在，但它们现在挂在系统用户上。
- `mobile_shift_reports` 已有 `owner_user_id`、`dingtalk_user_id`、`dingtalk_union_id` 字段。
- `work_order_entries` 已有 `created_by`、`created_by_user_id`、`machine_id`、`shift_id`、`business_date` 字段。
- `agent_profiles`、`communication_channels`、`agent_outbox_messages`、`chat_inbox`、`agent_runs`、`external_message_logs` 已存在。
- 当前 `同步钉钉成员` 前端写死 `department_id: 1`，后端只拉一个钉钉部门，不会递归组织架构。
- 当前用户删除接口实际是软删除，也就是停用账号，不是真正从数据库删除。

结论：系统缺的不是“再造一套用户系统”，而是补上“人员身份库”和“当班责任记录”。

## 3. 目标

第一目标：保留现有机台账号和二维码，不影响现场扫码填报。

第二目标：把钉钉人员作为真实人员身份来源，但不自动创建业务账号。

第三目标：每次填报都能追溯到“哪个机台账号提交、哪个人当班、什么时间提交、属于哪个业务日和班次”。

第四目标：AI Agent 能基于真实业务数据回答问题、催报、汇报异常，并能说明数据来源。

第五目标：账号页面从“同步用户”改为“身份绑定和责任治理”，避免误把钉钉通讯录变成系统账号。

## 4. 非目标

本设计不做以下事情：

- 不删除旧入口。
- 不重写 `/entry` 和 `/manage`。
- 不把钉钉人员全部同步为系统登录账号。
- 不把人员固定绑定到某台机。
- 不让大模型直接查数据库。
- 不允许 AI Agent 绕过 outbox 直接发钉钉消息。
- 不硬删除已有账号和历史数据。

## 5. 推荐方案

### 5.1 方案 A：机台账号不变，新增人员身份和当班责任记录

这是推荐方案。

做法：

- 机台账号继续用于二维码、填报入口、权限范围。
- 新增人员身份库，专门存真实人员和钉钉身份。
- 新增当班责任记录，记录每次填报对应的真实人员。
- 钉钉只做身份识别、通知和审批，不替代机台账号。

优点：

- 不破坏现有二维码。
- 不破坏历史填报。
- 适合轮班和代班。
- AI 可以查到真实责任人。
- 后续裁撤内勤统计岗时，责任链仍然清楚。

缺点：

- 需要多一层“人员身份”和“责任记录”页面。
- 第一次上线时需要处理已有账号和钉钉人员的匹配关系。

### 5.2 方案 B：把钉钉人员全部同步成系统用户

不推荐。

问题：

- 现场是机台二维码入口，不是每个人一个固定入口。
- 人员轮班后，账号权限会混乱。
- 同一个人可能今天在一台机，明天在另一台机。
- 会把账号页面变成一堆不参与业务流程的人员账号。

### 5.3 方案 C：只用机台账号，不记录人员

不推荐。

问题：

- 能知道哪台机填了，但不知道谁填的。
- 催报只能催机台，不能催具体人。
- 出现异常时责任追溯不清楚。
- AI Agent 不能准确回答“谁当班、谁负责、谁没报”。

## 6. 核心业务模型

### 6.1 机台账号

机台账号代表稳定业务入口。

字段含义：

- `user_id`：系统用户 ID。
- `username`：机台账号，例如某台机二维码对应的账号。
- `workshop_id`：所属车间。
- `team_id`：可选班组。
- `role`：机台、主操、电工、内勤、车间主任等系统角色。
- `is_mobile_user`：是否能进入手机端。
- `is_active`：是否启用。

规则：

- 机台账号不能因为人员变动而变。
- 机台账号可以停用，但默认不硬删。
- 机台账号不应该直接等于某个钉钉人员。

### 6.2 人员身份

建议新增 `person_identities` 表。

用途：保存真实人员身份，不作为业务登录账号。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 人员身份 ID |
| `display_name` | 人员姓名 |
| `dingtalk_user_id` | 钉钉用户 ID |
| `dingtalk_union_id` | 钉钉 union ID |
| `mobile_last4` | 手机号后四位，避免完整手机号暴露 |
| `workshop_id` | 默认所属车间，可为空 |
| `team_id` | 默认班组，可为空 |
| `status` | active / archived |
| `source` | dingtalk / manual |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

规则：

- 读取钉钉通讯录后，先生成“待绑定人员”，不自动创建系统用户。
- 人员可以归属默认车间，但不能固定绑定到单台机。
- 人员离职或不用时归档，不硬删。

### 6.3 当班责任记录

建议新增 `duty_person_attributions` 表。

用途：记录“这一次业务记录是谁填的、谁当班负责”。

建议字段：

| 字段 | 含义 |
|---|---|
| `id` | 责任记录 ID |
| `business_date` | 业务日 |
| `shift_config_id` | 班次 |
| `workshop_id` | 车间 |
| `equipment_id` | 机台 |
| `machine_user_id` | 机台账号 ID |
| `person_identity_id` | 实际人员 ID |
| `person_name_snapshot` | 当时显示的人名快照 |
| `dingtalk_user_id_snapshot` | 当时识别到的钉钉 ID 快照 |
| `source_table` | 来源表，例如 `mobile_shift_reports` |
| `source_record_id` | 来源记录 ID |
| `source` | dingtalk_auto / manual_select / admin_fix |
| `confidence` | 识别可信度，0 到 1 |
| `submitted_at` | 填报提交时间 |
| `created_at` | 创建时间 |

规则：

- 每次填报提交时都写一条责任记录。
- 一个机台账号一天可以对应多个人，因为会换班。
- 一个人一天也可以对应多台机，因为可能代班。
- 如果钉钉识别不到人，允许手动选择或手写姓名，但要标记为低可信。
- 管理员可以后补责任人，但必须留审计。

## 7. 手机端填报流程

### 7.1 钉钉 H5 打开

流程：

1. 员工扫机台二维码。
2. 系统通过二维码确定机台账号、车间、机台。
3. 如果在钉钉 H5 中打开，系统自动识别当前钉钉人员。
4. 页面显示“当前填报人：张三”，允许选择“不是本人 / 代班”。
5. 提交填报后，业务数据进入原有表，责任信息进入 `duty_person_attributions`。

### 7.2 普通浏览器打开

流程：

1. 员工扫机台二维码。
2. 系统仍然确定机台账号。
3. 页面提示选择当班人员。
4. 如果找不到人员，允许临时输入姓名。
5. 临时输入姓名需要在管理端显示为“待确认人员”。

### 7.3 历史记录

历史记录应同时显示：

- 业务日。
- 班次。
- 车间。
- 机台。
- 机台账号。
- 当班人员。
- 填报时间。
- 填报内容。
- 数据来源。

## 8. 管理端页面设计

### 8.1 账号页面改造

账号页面不再突出“同步钉钉成员”。

建议分成四块：

| 区域 | 用途 |
|---|---|
| 机台账号 | 管理二维码入口和系统账号 |
| 人员身份 | 查看钉钉人员和手工人员 |
| 当班责任 | 查看某天某班某台机是谁填的 |
| 绑定异常 | 查看未匹配、重复、离职、待确认人员 |

按钮建议：

- `读取钉钉通讯录`
- `生成待绑定清单`
- `绑定到人员身份`
- `解除钉钉绑定`
- `归档人员`
- `停用账号`

不建议继续使用：

- `同步钉钉成员`
- `删除用户`

原因：

- “同步成员”容易让人以为会同步完整组织架构并创建用户。
- “删除用户”容易让人以为会硬删历史责任。

### 8.2 当班责任页面

页面应支持筛选：

- 日期。
- 班次。
- 车间。
- 机台。
- 人员。
- 数据来源。
- 是否待确认。

表格应显示：

- 业务日。
- 班次。
- 机台。
- 机台账号。
- 当班人员。
- 钉钉识别状态。
- 填报时间。
- 填报来源。
- 关联业务记录。
- 操作：查看、纠正责任人、查看审计。

### 8.3 异常治理

需要新增或强化以下异常：

- 钉钉人员未匹配。
- 同一个钉钉人员匹配多个身份。
- 同一机台同一班次多人填报。
- 同一业务记录没有责任人。
- 手写人员超过指定次数。
- 机台账号被钉钉人员错误绑定。

## 9. AI Agent 设计

### 9.1 Agent 基本原则

AI Agent 不直接创造事实。

固定流程：

1. 识别提问人。
2. 识别提问来源，例如管理端、钉钉群、手机端。
3. 校验权限。
4. 查结构化业务数据。
5. 查 RAG 知识库。
6. 套固定回答模板。
7. 写入审计和运行记录。
8. 需要外发时进入 outbox。

禁止：

- 禁止大模型直接查数据库。
- 禁止没有数据时编数字。
- 禁止越权看其他车间。
- 禁止绕过 `agent_outbox_messages` 直接发钉钉。

### 9.2 Agent 最小角色

第一批建议保留以下 Agent：

| Agent | 作用 |
|---|---|
| 全厂总控 Agent | 回答全厂状态、产量、异常、日报摘要 |
| 车间状态 Agent | 回答指定车间状态、缺报、异常 |
| 催报 Agent | 识别缺报、迟报，通知责任人或车间群 |
| 产量 Agent | 回答上机、下机、包装、入库、在制 |
| 能耗 Agent | 回答电、气、吨耗、成本 |
| 质量 Agent | 回答质量异常、废料、成材率 |
| 知识 Agent | 从 RAG 中回答制度、口径、SOP |

### 9.3 回答模板

统一模板：

```text
【范围｜时间】状态：绿/黄/橙/红
结论：
关键数字：
原因：
建议动作：
数据来源：
可回复命令：
```

例子：

```text
【冷轧1650｜2026-06-17 长白班】状态：黄
结论：2#机已有填报，但当班人员未确认。
关键数字：本班填报 1 条，责任人可信度 0.4。
原因：当前记录来自普通浏览器，未识别到钉钉人员。
建议动作：车间主任在当班责任页面补确认责任人。
数据来源：mobile_shift_reports + duty_person_attributions。
可回复命令：查看2#机详情 / 今日缺报 / 责任人异常。
```

### 9.4 催报逻辑

催报应先找“责任人”，找不到再找“车间群”。

优先级：

1. 当前业务日、当前班次、当前机台已有责任人。
2. 上一班同机台最近责任人。
3. 该机台默认车间主任。
4. 车间钉钉群。
5. 管理员异常池。

同一异常 30 分钟内不重复刷屏。

## 10. 权限和安全

权限原则：

- 机台账号只能提交自己机台或自己范围内的数据。
- 人员身份不能直接登录管理端。
- 车间主任只能看本车间责任记录。
- 管理员可以维护人员身份和责任纠正。
- 钉钉群只能看绑定车间或全厂范围。

安全原则：

- 不把真实钉钉密钥写进前端。
- 不把完整手机号默认展示给普通用户。
- 人员归档不删除历史责任记录。
- 责任人纠正必须写审计。
- AI Agent 每次回答必须有数据来源。

## 11. 迁移策略

第一阶段：只新增表和只读页面。

- 新增 `person_identities`。
- 新增 `duty_person_attributions`。
- 读取钉钉通讯录只生成待绑定人员。
- 不改变现有填报保存逻辑。

第二阶段：填报提交时写责任记录。

- `/entry` 提交后写 `duty_person_attributions`。
- 没有识别到人员时允许手动选择。
- 历史页面显示责任人。

第三阶段：管理端治理。

- 账号页面改为机台账号、人员身份、当班责任、绑定异常四块。
- 车间主任页面显示本车间责任异常。
- 催报 Agent 使用责任记录找人。

第四阶段：AI Agent 完整接入。

- Agent 查询能回答谁填、谁缺报、谁当班。
- 钉钉消息从 outbox 发送。
- 外部发送结果写 `external_message_logs`。

## 12. 测试要求

后端测试：

- 读取钉钉通讯录不会自动创建系统用户。
- 钉钉人员可生成 `person_identities`。
- 同一个钉钉 ID 不能绑定多个 active 人员身份。
- 机台账号提交填报后会生成责任记录。
- 普通浏览器手动选择人员可以生成低可信责任记录。
- 车间主任只能看本车间责任记录。
- 管理员纠正责任人会写审计。
- 催报 Agent 优先使用责任人，再使用车间群。
- Agent 回答无数据时返回“数据不足”。
- outbox 去重和重试逻辑不被绕过。

前端测试：

- 账号页面不再出现容易误导的“同步钉钉成员”主按钮。
- 人员身份列表能展示待绑定、已绑定、已归档。
- 当班责任表能按日期、班次、车间、机台、人员筛选。
- 手机端填报能显示当前识别人员。
- 手机端可选择“代班 / 不是本人”。
- 历史填报能看到机台账号和当班人员。

浏览器 QA：

- 管理员打开账号页面，能看到机台账号和人员身份分区。
- 主操扫码进入填报，能识别机台。
- 钉钉 H5 打开时能识别人员。
- 普通浏览器打开时能手动选择人员。
- 车间主任只能看到本车间责任记录。
- AI 助手询问“谁没填、谁当班、哪个机台异常”时有事实来源。

## 13. 上线和回滚

上线原则：

- 先只读上线人员身份和责任页面。
- 再灰度一个车间写责任记录。
- 最后扩大到全部车间。

回滚方式：

- 新增表不影响旧业务。
- 如果责任记录写入失败，不阻断原有填报提交，但要记录错误日志。
- 前端保留旧字段兼容显示。
- 钉钉人员绑定失败时，不影响机台账号登录。

## 14. 验收标准

达到以下结果才算完成：

- 现场二维码填报不受影响。
- 系统能区分机台账号和真实人员。
- 每条新填报记录能查到当班责任人或明确显示待确认。
- 钉钉通讯录不会再自动制造无用系统账号。
- 账号页面能解释清楚“账号、人员、责任”的关系。
- AI Agent 回答责任、缺报、异常问题时有真实数据来源。
- 车间主任看不到其他车间责任记录。
- 所有外发消息先进 outbox，再写外部通讯日志。

## 15. 后续可扩展项

后续可以再做，但不是第一版必须：

- 接入正式排班表，提前知道每班应该是谁。
- 人脸或工牌识别作为人员确认方式。
- 责任人异常自动生成整改单。
- 按人员统计填报及时率。
- 按车间统计责任记录可信度。
- 将钉钉审批用于责任人纠正确认。

## 16. 自检结果

- 没有要求删除旧入口。
- 没有要求重写系统。
- 没有把钉钉人员直接当业务账号。
- 没有把人员固定绑定到机台。
- 没有让大模型直接查库或编数字。
- 方案可分阶段上线，失败时不会阻断原有填报。
