# MES 触发待补录设计方案

日期：2026-06-10
系统：鑫泰铝业 数据中枢

## 目标

把主操现场动作从“MES 一体机扫随行卡录下机数据，再扫机台二维码，再扫随行卡补录”简化为：

```text
MES 一体机扫随行卡并保存下机数据
  ↓
数据中枢自动抓到 MES 下机记录
  ↓
手机端扫机台二维码
  ↓
看到本机台待补录卷材
  ↓
点选卷材，只补 MES 没有的字段
```

正常情况下，主操不需要在手机端第二次扫随行卡。

## 核心判断

MES 一体机已经记录了产量相关的关键字段，因此产量类数据可以优先以 MES 为主账。

手机填报不再重复承担“产量真值”的职责，改为承担：

- 补录 MES 没有设计的现场字段。
- 确认这卷料确实属于当前机台。
- 补充异常、质量问题、备注、废料、套筒等现场信息。
- 在 MES 机列匹配不准时做人工兜底选择。

## 当前代码基础

系统已经具备以下基础，不需要从零开始：

- MES 卷材快照表：`mes_coil_snapshots`
- MES 工序记录表：`mes_workshop_process_records`
- MES 入库记录表：`mes_stock_records`
- 手机填报主表：`work_order_entries`
- 生产业务日口径：早上 `07:30` 到次日 `07:30`
- 手机扫码服务：`scan_lookup_service`
- MES 辅助字段服务：`mes_assisted_fill_service`
- 手机统一填报页：`UnifiedEntryForm.vue`

其中 `mes_workshop_process_records` 已有上机重量、下机重量、机台名、员工、工序、业务日等字段，适合生成“待补录卷材”。

| 数据类型 | 主来源 | 手机端作用 |
| --- | --- | --- |
| 随行卡号 | MES | 展示、关联，不要求重复扫码 |
| 客户 | MES | 展示 |
| 合金 | MES | 展示 |
| 规格 | MES | 展示 |
| 当前工艺 | MES | 展示和匹配 |

| 机列 | MES 设备名优先，本系统机台二维码兜底 | 确认归属 |
| 业务日 | 数据中枢统一按 07:30 口径计算 | 不让用户手填 |
| 废料 | 手机补录 | 人工填写 |
| 套筒/托盘 | 手机补录 | 人工填写 |

| 异常原因 | 手机补录 | 人工填写 |
| 备注/照片 | 手机补录 | 人工填写 |

## 推荐方案

### 方案 A：动态待补录列表，第一阶段推荐

不新增大表，后端根据 MES 工序记录实时计算“哪些卷材还没补录”。

计算逻辑：

1. 按当前机台、车间、业务日查询 MES 工序记录。
2. 用 `device_name` 优先匹配本系统机台。
3. 如果 MES 没有明确机台，则用车间 + 工艺 + 机台别名做候选匹配。
4. 排除已经存在本地补录记录的卷材。
5. 返回待补录列表给手机端。

优点：

- 改动小。
- 不容易产生脏草稿。
- MES 数据更新后，待补录列表能自然刷新。

缺点：

- 如果用户需要“已忽略、已确认不是本机”的状态，后续需要增加一张轻量状态表。

### 方案 B：自动生成草稿表

MES 每同步一条下机记录，就生成一条本地草稿。

优点：

- 追溯清晰。
- 能记录待办状态。

缺点：

- 更容易出现重复草稿、过期草稿。
- 需要更多清理逻辑。

### 方案 C：继续扫码随行卡

保留现在的“扫随行卡带出字段”作为主流程。

优点：

- 实现最简单。

缺点：

- 没有解决现场最痛的问题，主操仍然要重复扫随行卡。

结论：第一阶段采用方案 A，保留方案 C 作为兜底，不直接采用方案 B。

## 手机端交互

主操扫机台二维码进入填报端后，页面顶部显示：

```text
当前机台：园区在线退火 1#线
业务日：2026-06-10
待补录：3 卷
```

中间显示待补录列表：

```text
26A04967
0.96*1220*C｜1060 H24｜河南永晟
下机 6.35 吨｜10:52｜MES 已入账
按钮：补录
```

点击“补录”后进入简化表单：

- MES 已有字段只展示，不要求重复填。
- 手机端只显示需要人工补充的字段。
- 没有质量问题时，只点一次确认即可提交。
- 有质量问题时，再展开问题类型、描述、照片。

保留一个小入口：

```text
找不到卷材？扫随行卡兜底
```

这个入口只用于 MES 延迟、机列匹配失败、临时补录等异常场景。

## 机列匹配规则

匹配分三级：

| 等级 | 规则 | 处理方式 |
| --- | --- | --- |
| 高可信 | MES `device_name` 能直接匹配本系统机台别名 | 自动归到该机台 |
| 中可信 | MES 只有车间和工艺，能推断到少数候选机台 | 手机端让主操点选 |
| 低可信 | MES 只有随行卡或批号，没有可靠机台信息 | 不自动归属，只能扫码兜底 |

如果 MES 机台和当前机台二维码不一致，页面提示：

```text
这卷料在 MES 中显示为其他机台，请确认是否扫错机台。
```

默认不阻断，但必须记录差异。

## 数据保存方式

第一阶段不把 MES 记录伪装成人工填报记录。

提交补录时写入 `work_order_entries`：

- `machine_id`
- `workshop_id`
- `business_date`
- `on_machine_time`
- `off_machine_time`
- `input_weight`
- `output_weight`
- `input_spec`
- `output_spec`
- `material_state`
- 人工补录字段
- `extra_payload.mes_reference`

其中产量字段来自 MES，人工补录字段来自手机端。

`extra_payload.mes_reference` 保存：

- MES 工序记录 ID
- 随行卡号
- MES 机台名
- MES 员工名
- MES 保存时间
- 匹配等级
- 匹配方式

这样管理端既能按 MES 主账统计，也能追溯是谁在手机端补录了现场字段。

## 统计口径

产量主口径：

- 全厂最终产量：继续取 MES 入库/包装入库口径。
- 车间过工序产量：取 MES 工序记录下机重量。
- 机台产量：取 MES 工序记录，并通过机台匹配归属。

手机端补录不再直接改写产量真值。

如果人工认为 MES 错了，不直接覆盖 MES 主账，而是走“纠错/差异记录”：

```text
MES 下机重量：6.35 吨
现场认为：6.30 吨
原因：现场复核发现一处录入误差
```

管理端可以展示差异，但日报主口径仍以 MES 为准，除非管理端明确走审批纠偏。

## 接口设计

新增或扩展接口：

```text
GET /api/v1/mobile/mes-pending-supplements
```

用途：当前机台登录后，获取本机台待补录卷材。

入参：

- 当前登录用户或机台二维码身份。
- 可选 `business_date`，默认当前生产业务日。

返回：

- 待补录卷材列表。
- MES 字段。
- 机台匹配等级。
- 是否已补录。
- 是否存在机台不一致风险。

提交接口可复用现有手机填报保存接口，但需要支持传入：

```text
mes_process_record_id
mes_reference
supplement_fields
```

## 后端执行阶段

### 阶段 1：只读核对

目标：确认 MES 下机记录是否稳定包含机台、随行卡、重量、员工、时间。

验证：

- 抽取最近 100 条 MES 工序记录。
- 统计有机台名的比例。
- 统计有下机重量的比例。
- 统计能匹配到本系统机台的比例。
- 找出不能匹配的机台名，补别名。

通过标准：

- 下机重量完整率达到可用水平。
- 高可信或中可信机台匹配率达到现场可接受水平。
- 未匹配原因能列清楚。

### 阶段 2：后端待补录服务

目标：按机台返回待补录卷材列表。

验证：

- 同一业务日只返回当前机台范围。
- 已补录卷材不再出现在待补录列表。
- MES 延迟或无数据时返回空列表，不报错。
- 机台不一致时返回风险标记。

### 阶段 3：手机端简化补录

目标：手机端显示“待补录列表”，点选后只填 MES 没有的字段。

验证：

- 不再要求正常流程第二次扫随行卡。
- 没有质量问题时可以一键确认。
- 有问题时可以展开补充。
- 找不到卷材时仍可扫随行卡兜底。

### 阶段 4：管理端对账

目标：管理端能看懂 MES 主账、手机补录、差异。

验证：

- 填报明细不把 MES 原始记录当成人工填报。
- 能看到哪些 MES 下机记录尚未补录。
- 能看到机台匹配失败原因。
- 能看到 MES 值和人工补录字段。

### 阶段 5：灰度切换

目标：把主操产量填报逐步从“人工录产量”切到“MES 产量主账 + 人工补录”。

验证：

- 先开一个车间或一类工序。
- 连续观察 3-7 天。
- 如果缺失、错配、延迟都可控，再扩大范围。

## 不做的事

- 不让手机端直接连接 SQL Server。
- 不把 MES 数据写回 MES。
- 不删除现有扫码随行卡兜底入口。
- 不立刻删除旧字段和旧表。
- 不把 MES 原始数据混进“人工填报明细”。
- 不让前端用假动画掩盖后端数据延迟。

## 风险和处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| MES 机台名不完整 | 待补录挂错机台 | 用别名映射和匹配等级控制 |
| MES 保存延迟 | 手机端暂时看不到刚下机卷材 | 保留扫随行卡兜底 |
| 同一车间多条相似线 | 自动匹配不准 | 中可信时让主操点选 |
| MES 重量录错 | 日报主口径受影响 | 管理端做差异和审批纠偏 |
| 手机补录漏填 | 现场字段缺失 | 待补录列表保留未完成状态 |
| 旧报表仍读手机产量 | 数字口径不一致 | 阶段 4 统一管理端展示 |

## 测试清单

后端测试：

- MES 工序记录转待补录列表。
- 机台别名匹配。
- 业务日 07:30 边界。
- 已补录记录排除。
- 机台不一致风险标记。
- MES 无数据时不报 500。

前端测试：

- 扫机台二维码后能看到待补录列表。
- 点选卷材后只显示补录字段。
- 质量问题默认收起。
- 扫随行卡兜底仍可用。
- 小屏幕不溢出。

业务测试：

- 在线退火一条线试跑。
- 冷轧一条线试跑。
- 一卷正常补录。
- 一卷 MES 延迟补录。
- 一卷机台不匹配补录。
- 一卷有质量问题补录。

## 验收标准

- 正常流程下，主操不需要在手机端第二次扫随行卡。
- 手机端能按当前机台看到待补录卷材。
- 产量主账来自 MES，不再靠手机端重复输入。
- 手机端仍能补 MES 没有的字段。
- 管理端能区分 MES 主账、手机补录、差异纠偏。
- 出错时有兜底路径，不阻断现场填报。

## 推荐下一步

先执行阶段 1：只读核对 MES 最近工序记录。

如果数据证明 MES 机台名和下机重量可用，再进入阶段 2 和阶段 3。

如果阶段 1 发现 MES 机台名缺失严重，就先补机台别名映射，不急着改手机端。
