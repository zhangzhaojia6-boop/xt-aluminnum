# 登录、权限、健康检查审计

日期：2026-06-11

范围：只读检查线上真实环境、登录接口、管理端路由、填报端入口、健康检查、MES 同步状态。

## 1. 结论

当前线上登录接口本身可用，管理员账号可以通过 `/api/v1/auth/login` 正常拿到访问令牌。线上健康检查总体正常，`/healthz`、`/api/v1/healthz`、`/readyz` 都返回正常。

需要继续修复或纳入计划的问题有 4 个：

1. `/api/v1/readyz` 仍然是 404，健康检查路径没有完全统一。
2. 后端已经返回 `refresh_token`，但前端只保存短期访问令牌，401 时直接退出登录，没有自动续期。
3. 管理端账号打开 `/entry` 和 `/entry/history` 时，路由会回到管理端，但页面短时间可能为空白，体验不够清楚。
4. 自动化测试如果用 `networkidle` 等待实时页，会因为 SSE 长连接误判超时；必须改成等待关键卡片或接口返回。

### 登录接口

`/api/v1/auth/login` 返回 200，角色为 `admin`，同时返回 `access_token` 和 `refresh_token`。

这说明“登录不上”不一定是密码错误，也不一定是后端完全不可用。更可能的原因包括：

1. 前端请求被浏览器、代理或页面跳转取消。
2. 访问令牌过期后没有自动续期，用户被动退出。
3. 健康检查路径或前端 API 基础路径不一致，导致部分测试报错。

## 3. 代码链路证据

### 后端健康检查

文件：`backend/app/main.py`

已存在：

1. `/health`
2. `/healthz`
3. `/api/v1/healthz`
4. `/readyz`

缺失：

1. `/api/v1/readyz`

文件：`backend/app/core/health.py`

`/readyz` 的 503 主要由数据库、上传目录、自动流水线硬门禁决定。MES 同步状态会放入返回详情，但当前代码没有因为 MES stale/failed 直接把 `readyz` 拉成 503。

这点是好事：外部 MES 短暂异常，不应该直接让部署健康失败。

### 前端网络错误提示

文件：`frontend/src/api/index.js`

当前错误文案规则：

| 情况 | 前端提示 |
| --- | --- |
| timeout | 请求超时，服务器响应太慢，请稍后重试 |
| ERR_NETWORK | 连接服务器失败，请检查网络、代理或稍后重试 |
| 500+ | 服务器暂时不可用，请稍后重试 |
| 401 | 清空登录并跳转登录页 |

风险：前端没有使用后端返回的 `refresh_token`。如果访问令牌过期，会直接退出登录，让现场用户误以为“又登录不上”。

### 路由权限

文件：`frontend/src/router/guardRules.js`

当前规则大意：

1. 填报端账号只能去 `/entry`。
2. 车间主任只能看对应车间看板。
3. 管理端账号访问 `/entry` 会被引导回管理端。
4. 手机窄屏下，管理端只允许进入部分核心页面。

风险：管理员点“操作员端”时没有明确告诉用户“当前账号不是填报账号”，容易误解为空白或加载失败。

## 5. 必须修复

### P1：前端登录续期

问题：后端有 `refresh_token`，前端没有保存和使用。

影响：用户长时间开页面后，访问令牌过期会直接退出登录，容易被误解为服务器或密码问题。

建议：

1. 前端保存 refresh token。
2. 401 时先调用 `/auth/refresh`。
3. 刷新成功后重放原请求。
4. 刷新失败才退出登录。

验证：

1. 单元测试：401 后能调用 refresh。
2. 单元测试：refresh 失败才 logout。
3. 浏览器测试：管理端长会话不无故掉线。

### P1：统一健康检查路径

问题：`/api/v1/readyz` 为 404。

影响：监控、部署脚本、QA 脚本如果写了 API 前缀，会误报后端不健康。

建议：

1. 增加 `/api/v1/readyz`。
2. 文档统一推荐 `/healthz` 和 `/readyz`。
3. 部署探针使用 `/readyz`，外部数据源健康单独用 `/api/v1/mes/sync-status`。

验证：

1. `/readyz` 返回 200。
2. `/api/v1/readyz` 返回同样结构。
3. MES stale 不直接让部署探针失败，除非明确开启硬门禁。

### P2：管理员进入填报端提示

问题：管理员访问 `/entry` 可能短暂空白或被直接带回管理端。

影响：用户不知道是没有权限、页面坏了，还是网络失败。

建议：

1. 管理端下拉里的“操作员端”只对有填报权限的账号显示。
2. 管理员访问 `/entry` 时显示友好页，说明“当前账号是管理端账号，请使用机台二维码或填报账号进入”。
3. 提供“返回管理端”按钮。

验证：

1. 管理员访问 `/entry` 不出现空白。
2. 填报账号访问 `/entry` 正常。
3. 手机端车间主任仍能进入车间看板。

### P2：QA 等待规则

问题：实时页使用 SSE 长连接，`networkidle` 会误判。

影响：测试报告会把正常长连接当成失败。

建议：

1. `/manage/live` 等待 `data-testid="manage-live"`。
2. 再等待 `/api/v1/aggregation/live` 成功返回。
3. 最后断言 MES 包装产量、机列数量、实时状态。

验证：

1. 线上单页等待 12 秒能显示 `284.84 吨`。
2. 不再把 `ERR_ABORTED` 的跳页取消请求当成阻塞故障。

## 6. 和 MES 主数据改造的关系

这份审计对后续“MES 主数据 + 手机补录 + 实时大屏”有三个约束：

1. MES 同步健康要继续显示在管理端，但不要直接拖垮部署健康。
2. 实时大屏要显示“加载中、暂无同步、真实 0、异常隔离”四种不同状态。
3. 手机补录和车间主任看板必须先解决登录续期和权限提示，否则现场扫码体验会不稳定。
