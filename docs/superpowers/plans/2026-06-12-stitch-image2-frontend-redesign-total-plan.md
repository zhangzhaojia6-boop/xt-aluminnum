# 鑫泰铝业 数据中枢：Stitch + image2 前端重构总计划

日期：2026-06-12

## 目标

本计划用于指导后续前端视觉重构、业务链路核对和系统稳定性验收。目标不是单纯把页面做“炫”，而是在不破坏现有业务逻辑、后端算法、数据库映射和权限体系的前提下，让 `鑫泰铝业 数据中枢` 的前端页面更美观、更清晰、更像真实工业数据产品。

核心目标：

1. 使用 image2 生成目标视觉方向，再通过 Stitch 输出页面级设计稿。
2. 将 Stitch 设计稿与真实业务页面、真实接口、真实数据库字段对齐。
3. 审查并修复前端映射、业务口径、算法展示、权限边界、路由入口、页面性能等问题。
4. 用浏览器实际测试所有关键用户会使用到的功能模块，确认功能可用。
5. 每个阶段完成后做多视角 review，避免只看视觉、不看业务。

## 已确认前提

1. 当前仓库没有未提交改动，适合从干净状态开始做计划和分阶段实施。
2. CodeGraph 已可用，当前项目索引正常，可用于理解前后端代码结构。
3. Stitch MCP 已可用，并能看到已有的工业蓝相关设计项目。
4. 前端是 Vue 3 + Vite + Element Plus + Pinia + Vue Router + ECharts。
5. 产品名称统一为 `鑫泰铝业 数据中枢`。
6. 不能把本系统称为 MES 系统，MES 只能作为外部数据来源、外部接口或边界系统。

## 设计原则

1. 真实业务优先，视觉服务于生产判断。
2. 页面必须清楚展示数据来源，不能把 MES 数据、人工填报数据、算法计算数据混在一起。
3. 动效只能用于状态变化、实时数据变化和交互反馈，不能为了好看影响性能。
4. 工业蓝是主视觉，但不要做成泛滥的霓虹风、AI 风、模板风。
5. 管理端保持高密度信息布局，手机端保持大字、少按钮、强状态、少滚动。
6. 不新增无意义解释文案，不增加不必要的复杂度。
7. 不删除页面、接口、角色或字段，除非先完成依赖追踪和风险确认。

## 第一阶段：只读理解全系统

目的：先把系统看明白，不急着写代码。

执行内容：

1. 阅读前端路由、页面、布局、组件、设计变量和样式文件。
2. 阅读后端路由、服务层、领域计算器、数据库模型、适配层和定时任务。
3. 梳理管理端、填报端、车间主任端、调度大屏、日报、生产分析、能耗、异常、人员配置等页面。
4. 梳理 MES 外部数据、人工填报数据、算法计算数据、日报归档数据分别从哪里来。
5. 梳理当前未提交改动、最近提交、部署脚本和云端同步方式。

输出物：

1. 页面清单。
2. 数据链路清单。
3. 接口清单。
4. 权限角色清单。
5. 高风险区域清单。

验收标准：

1. 能说清每个核心页面的数据从哪里来。
2. 能说清每个核心指标是直接读取、人工填报还是算法计算。
3. 能说清哪些页面适合重构，哪些页面只能小修。

## 第二阶段：现状浏览器审查

目的：用真实使用方式发现问题，不只看代码。

执行内容：

1. 启动本地前后端环境。
2. 用浏览器打开核心页面并截图留档。
3. 测试管理员、车间主任、填报角色等关键用户路径。
4. 检查页面入口、导航、按钮、表格、筛选、日期选择、异常提示、空状态、加载状态。
5. 检查手机端填报、历史填报、扫码入口、车间看板是否可用。

重点页面：

1. `/manage/live`
2. `/manage/today`
3. `/manage/production`
4. `/manage/workshop-dashboard`
5. `/manage/coils`
6. `/manage/fill-details`
7. `/manage/energy`
8. `/manage/alerts`
9. `/manage/admin/settings`
10. `/manage/admin/users`
11. `/entry`
12. `/entry/fill`
13. `/entry/coil`
14. `/entry/history`

输出物：

1. 截图基线。
2. 可用性问题清单。
3. 视觉一致性问题清单。
4. 性能和响应慢问题清单。
5. 阻塞用户完成任务的问题清单。

验收标准：

1. 每个核心页面至少有一次真实浏览器验证记录。
2. 每个发现的问题都能说明触发条件和业务影响。

## 第三阶段：image2 生成视觉方向

目的：先确定“整体长什么样”，避免每个页面各做各的。

执行内容：

1. 基于现有工业蓝主视觉和用户参考图，生成数据中枢目标视觉方向。
2. 形成桌面大屏、管理端页面、手机端页面三类视觉基准。
3. 控制视觉风格为工业蓝、精密仪表、真实数据中枢，不做营销页。
4. 明确哪些图形元素可以用，哪些元素禁止用。

输出物：

1. 目标视觉方向图。
2. 颜色、字体、卡片、表格、指标、状态、动效的视觉规则。
3. 不允许出现的视觉问题清单。

验收标准：

1. 视觉方向与真实工业管理系统一致。
2. 不使用会明显拖慢页面的重光效。
3. 不出现假数据展示和纯装饰大屏。

## 第四阶段：Stitch 输出页面级设计稿

目的：让 Stitch 先完成页面设计，再迁移真实业务数据。

执行内容：

1. 将目标视觉规则整理为 Stitch 可理解的设计说明。
2. 用 Stitch 为核心页面生成页面级设计稿。
3. 每个设计稿都必须考虑真实字段、真实表格、真实筛选、真实权限。
4. 设计稿中的数字只作为占位，不能当成真实业务数据。
5. 设计稿完成后先做 design review，再进入代码实现。

页面优先级：

1. 第一优先级：`/manage/live`、`/manage/today`、`/manage/production`。
2. 第二优先级：`/manage/workshop-dashboard`、`/manage/coils`、`/manage/fill-details`、`/manage/energy`。
3. 第三优先级：`/manage/alerts`、`/manage/admin/settings`、`/manage/admin/users`。
4. 第四优先级：手机填报端和车间主任端。

输出物：

1. Stitch 项目链接。
2. 页面级设计稿清单。
3. 每个页面的布局说明。
4. 每个页面的数据区域和接口占位说明。

验收标准：

1. Stitch 设计稿与 image2 目标方向一致。
2. 页面布局能承载真实业务字段。
3. 页面不是“漂亮但不能用”的静态图。

## 第五阶段：前后端映射冻结

目的：在写 UI 前，先把数据对齐，避免前端显示错字段。

执行内容：

1. 为每个页面建立字段映射表。
2. 标明每个字段来自哪个接口、哪个数据库表、哪个算法或哪个外部来源。
3. 标明时间口径，例如业务日、自然日、班次、日报归档时间。
4. 标明权限规则，例如管理员、车间主任、内勤、主操、电工分别能看什么。
5. 标明空值规则，例如没有数据时显示 0、空状态、未同步、未填报还是不适用。

输出物：

1. 页面字段映射表。
2. 接口字段映射表。
3. 数据库字段映射表。
4. 业务时间口径表。
5. 权限可见性表。

验收标准：

1. 每个前端展示字段都能追溯到真实来源。
2. 每个算法指标都能说明计算公式。
3. 不允许前端为了好看改字段含义。

## 第六阶段：小步实现前端

目的：逐页替换，不大爆炸式改造。

执行内容：

1. 先统一设计变量，例如颜色、字体、间距、卡片、表格、状态色。
2. 再抽取可复用基础组件，例如指标卡、状态条、数据表、筛选栏、实时数字、异常卡片。
3. 按页面优先级逐页实现。
4. 每改完一个页面，就跑对应测试和浏览器验证。
5. 保留真实接口调用，不用假数据替代。
6. 如果后端字段不够，先记录问题，不擅自改数据库。

输出物：

1. 页面实现代码。
2. 组件实现代码。
3. 每页修改前后截图。
4. 每页测试记录。

验收标准：

1. 页面能正常打开。
2. 数据能正常加载。
3. 筛选、分页、跳转、刷新、权限都正常。
4. 移动端不溢出。
5. 页面响应速度不能明显变慢。

## 第七阶段：业务、算法、数据库映射审查

目的：确保视觉重构没有改坏业务。

执行内容：

1. 审查产量、包装产量、入库产量、成品率、废料、能耗、合同量、在制料等指标。
2. 审查 MES 数据和人工填报数据是否被正确区分。
3. 审查日报、今日、生产分析、调度大屏的数据时间口径是否一致。
4. 审查填报端提交字段是否进入正确数据库字段。
5. 审查管理端展示字段是否来自正确接口。
6. 审查权限是否存在越权或误隐藏。

输出物：

1. 指标口径核对表。
2. 数据库映射核对表。
3. 前端字段核对表。
4. 风险问题清单。

验收标准：

1. 没有发现前端字段错接。
2. 没有发现算法展示口径混乱。
3. 没有发现权限边界明显错误。

## 第八阶段：多视角 review

目的：不只从程序员角度看，也从真实业务角度看。

审查视角：

1. CEO 视角：是否能让管理层更快看懂生产经营情况。
2. 工程师视角：代码是否简单、稳定、可维护。
3. 设计师视角：页面是否美观、统一、清晰、没有 AI 味。
4. 安全审查员视角：权限、数据、密钥、接口、日志是否安全。
5. 真实用户视角：现场人员是否能快速完成填报和查看。

输出物：

1. 五视角评分。
2. 扣分原因。
3. 最短补齐路径。
4. 是否允许进入下一阶段的结论。

验收标准：

1. 每个视角评分不低于 9.5 分。
2. 如果低于 9.5 分，必须先修复再继续。

## 第九阶段：QA 和浏览器全流程测试

目的：用证据证明系统可用，不靠口头保证。

测试内容：

1. 前端构建测试。
2. 后端测试。
3. 接口测试。
4. 浏览器页面测试。
5. 手机端适配测试。
6. 权限测试。
7. 表单提交测试。
8. 历史记录测试。
9. 异常状态测试。
10. 数据为空、接口失败、加载慢场景测试。
11. 核心业务路径回归测试。

核心业务路径：

1. 管理员登录并查看调度大屏。
2. 管理员查看昨日报表。
3. 管理员查看生产分析。
4. 管理员查看填报明细。
5. 管理员查看能耗和异常。
6. 车间主任查看本车间看板。
7. 主操扫码进入填报。
8. 电工扫码进入填报。
9. 内勤提交日报类数据。
10. 用户查看历史填报。

输出物：

1. 测试命令和结果。
2. 浏览器验证截图。
3. 失败问题清单。
4. 修复后复测记录。

验收标准：

1. 关键页面没有阻塞错误。
2. 核心业务路径能走通。
3. 没有明显页面溢出、空白、卡死、接口错接。

## 第十阶段：提交和同步云端

目的：在确认无误后再进入交付。

执行内容：

1. 汇总所有改动。
2. 再次检查 git diff。
3. 运行最终测试。
4. 按 gstack ship 流程提交。
5. 同步云端生产环境。
6. 做上线后浏览器验证。
7. 如果发现线上问题，按回滚方案处理。

输出物：

1. Git 提交记录。
2. 云端同步结果。
3. 上线后验证结果。
4. 剩余风险清单。

验收标准：

1. 本地测试通过。
2. 云端页面可打开。
3. 关键页面数据正常。
4. 没有登录、路由、权限、接口的阻塞问题。

## 风险控制

1. 不在未确认数据来源前替换指标口径。
2. 不在未确认依赖前删除页面、接口、字段、角色。
3. 不使用假数据冒充真实业务数据。
4. 不引入重型动画库，除非确实必要并通过性能测试。
5. 不把 Stitch 设计稿直接当成最终代码，必须接回真实后端数据。
6. 不为视觉效果破坏现有权限和业务流程。
7. 不把系统叫成 MES 系统，避免产品定位混乱。
