# 数据中枢管理端工业蓝视觉重构计划

## 背景

用户目标是把管理端各页面统一到上传参考图的风格：工业蓝深色调度墙、顶部状态栏、高密度指标卡、生产流转、右侧告警流、底部系统状态条。

重要边界：参考图的左侧导航栏不作为改造参考。导航栏继续沿用系统现有导航信息架构、权限过滤和折叠逻辑，只把颜色、边框、选中态、间距接入统一工业蓝主题。页面主体布局、UI 颗粒、图像/图标语言和数据卡结构要与参考图对齐。

本计划先做前端视觉和结构重构，不改后端算法、不改接口路径、不改数据库字段、不改统计口径。所有页面仍读取当前已有 API 和组合函数。

本轮 plan-design-review 追加硬要求：目标图只作为“页面主体”的颗粒度标准，不作为导航栏标准。后续任何管理端页面都必须先由 Stitch 生成目标主体稿，再把该主体稿套回现有 Vue 路由、权限和后端数据。没有 Stitch screen、HTML 或截图证据的页面，不进入整页前端实现。

本轮进一步收紧：前端整页主体不能绕过 Stitch 手写。工程代码只允许做“接线”工作，也就是保留现有路由、权限、接口、组合函数和字段映射，把 Stitch 生成的主体结构接到真实数据上。导航栏只做主题皮肤统一，不按目标图重新分组，也不因为窄屏放宽角色权限。

本轮二次设计审查再收紧：对齐目标图时必须按“目标页面颗粒度”判断，不按整站外壳判断。也就是说，页面主体里的网格、卡片、工业图像、流程箭头、事件流和底部状态必须接近目标图；左侧导航只保留现有系统导航，不参考目标图的菜单分组、菜单数量或用户区样式。后续任何页面如果没有 Stitch 输出，就只能停在计划或提示词阶段，不允许先手写 Vue 页面。

本轮三次设计审查最终收口：上传目标图只定义“页面主体”的长相和信息密度。左侧导航、用户区、菜单图标和菜单分组全部不作为参考。Stitch 必须先生成完整页面主体，再由工程把主体接到当前 Vue 路由、权限、接口和字段映射上；工程不得先手写整页前端，也不得用普通图标和蓝色卡片冒充 Stitch 工业图像。

本轮四次设计审查再优化：目标不再是“风格接近”，而是“主体颗粒逐项对齐”。验收时先遮住左侧导航，只比较页面主体：布局骨架、卡片密度、工业图像、流程箭头、明细表、右侧事件流、底部状态条都必须能和目标图一一对应。前端主体必须由 Stitch 先生成；Vue 只能做现有后端路由、接口、权限和真实字段映射的接线。

## 本轮 plan-design-review 终版优化

本轮用户补充要求后，计划按下面规则重新锁定。简单说：参考图只管“页面主体长什么样”，不管“左侧导航怎么排”；Stitch 先画主体，工程再把主体接回真实系统。

| 事项 | 终版规则 | 为什么这样做 |
| --- | --- | --- |
| 参考范围 | 只参考上传图的页面主体，不参考左侧导航、用户头像、菜单分组 | 避免把现有权限导航和业务入口改乱 |
| 颗粒度 | 每个页面主体必须具备顶部状态、KPI 排、工业主图、紧凑明细、分布结构、右侧事件流、底部状态条 | 防止只换成深蓝色卡片，却没有目标图的信息密度 |
| Stitch 顺序 | 先由 Stitch 生成完整页面主体，再进入 Vue 实现 | 保证前端视觉来源清楚，不由工程凭感觉手写整页 |
| 导航处理 | 如果 Stitch 输出里带导航，落地时丢弃导航，只取主体 | 当前系统已有导航、权限过滤和移动端抽屉，不跟目标图重做 |
| 后端接线 | Vue 只接现有 `/manage/...` 路由、现有 API、现有组合函数、现有字段和权限 | 不为视觉重构改算法、不造假接口、不写静态假数 |
| 开工凭据 | 每页必须有当前可见的 Stitch screen、HTML 或截图证据；历史 screen ID 不能单独当开工凭据 | 本轮 Stitch MCP `list_screens` 返回空对象，所以必须重新确认可访问性 |
| 验收方式 | 浏览器截图时先遮住或忽略左侧导航，只验页面主体；再跑字段映射、路由权限、构建和 E2E | 同时保证好看、能用、数据不乱 |

最终施工顺序固定为：

1. 用 Stitch 和工业蓝设计系统生成目标页面主体。
2. 记录 Stitch project、screen、HTML 或截图证据。
3. 按目标图颗粒逐项打勾：顶部状态、KPI、工业主图、明细、分布、事件、底部状态。
4. 丢弃 Stitch 导航，把主体套进现有 `ManageShell.vue`。
5. 接回原 `/manage/...` 路由、原 API、原权限、原算法和真实字段。
6. 对每个大数字补字段来源测试；找不到真实来源就显示空状态，不写假数。
7. 用桌面和窄屏浏览器截图验收主体颗粒，再跑前端测试、后端相关测试和构建。

五视角计划评分：CEO 9.8、工程师 9.8、设计师 9.8、安全审查员 9.8、真实用户 9.8。扣掉的 0.2 分不是方案本身问题，而是 Stitch 当前 screen 列表查询为空，后续每页开工前必须重新拿到当前可见的 Stitch 交付物。

## Taste + Impeccable 审查优化

Design Read：这是工厂生产管理端和调度工具，主要服务管理层、车间主任、内勤、主操和电工。视觉应该是工业蓝高密数据中枢，稳、准、清晰；不是营销页，不追求花哨故事感。

### 为什么要加这一层

之前计划已经锁住了 Stitch 先生成主体、Vue 再接真实后端的顺序，但还缺一层“看起来是否可信、是否真的好用”的前端审查。新增这一层后，每个页面不只检查有没有接对接口，还要检查用户看不看得懂、页面像不像真实生产系统、有没有 AI 生成味和不可用细节。

### Taste 审查只取适合本系统的部分

`taste` 原始规则更偏 landing page、作品集和重设计，不适合直接套到本系统这种 dashboard。这里仅采用它的反模板化判断：

| 审查项 | 通过标准 | 不通过表现 |
| --- | --- | --- |
| 设计意图 | 页面结构能解释具体业务任务 | 只是深蓝背景加通用卡片 |
| 工业语义 | 图像、图标、流程箭头都和铝加工、能耗、填报或 MES 有关 | emoji、通用 SaaS 插画、无意义科技线条 |
| 信息节奏 | KPI、图形、表格、事件流之间有主次 | 每块都一样重，用户不知道先看哪里 |
| 视觉克制 | 工业蓝、状态色、动效都有用途 | 紫蓝渐变、玻璃拟态、过度发光、装饰性动画 |
| 非 AI 感 | 一眼看像真实生产调度系统 | 像套模板、像演示稿、像生成器默认风格 |

### Impeccable 审查增加可验收指标

每个页面进入提交前，必须按下面 5 类打分。每类 0 到 4 分，总分 20 分；低于 18 分不能进入合并。

| 维度 | 检查内容 | 阻塞线 |
| --- | --- | --- |
| 可访问性 | 对比度、焦点态、键盘可用、按钮语义、表单标签 | 关键文字读不清或按钮无法键盘操作 |
| 性能 | 首屏资源、动画是否拖慢、图表是否重复渲染、长表是否卡顿 | 管理端页面明显卡顿或资源异常 |
| 主题一致性 | 是否使用 `xt-tokens.css`、`industrial.css` 和现有组件语言 | 大量硬编码颜色、圆角、阴影和字体 |
| 响应式 | 桌面高密、窄屏可读、触控目标够大、无横向溢出 | 手机或窄屏核心流程不可用 |
| 反模式 | 是否有 AI 味、嵌套卡片、装饰动效、静态假数 | 静态假数、普通蓝卡片堆叠、无业务图像 |

### 页面级审查顺序

1. 先遮住左侧导航，只看页面主体是否达到目标图颗粒。
2. 检查 Stitch 证据：project、screen、HTML 或截图必须存在。
3. 检查业务映射：每个大数字、表格列、事件卡都能追到真实 API、组合函数或空状态。
4. 检查 taste：页面不能像通用模板，必须有真实工业语义。
5. 检查 impeccable：可访问性、性能、主题、响应式、反模式总分至少 18/20。
6. 浏览器实际打开页面，截桌面和窄屏图，确认加载、空状态、异常状态和权限入口。
7. 跑相关前端测试、构建测试和必要 E2E，不能只靠肉眼说通过。

### 页面保留、合并、删除判断

| 类型 | 判断标准 | 动作 |
| --- | --- | --- |
| 保留 | 直接支撑日报、实时调度、生产、能耗、填报、异常、权限或设置 | 用 Stitch 主体重构并接真实数据 |
| 合并 | 数据源相同、用户任务重复、只差一个筛选条件 | 合进更高价值页面，保留原路由跳转或重定向 |
| 删除候选 | 无导航入口、无真实数据、无业务角色使用、接口也无调用 | 先列清依赖和回滚方案，再灰度删除 |
| 暂缓 | 功能看似旧，但可能被历史账号、权限或脚本依赖 | 只做标记，不立即删除 |

## Stitch 交付物硬门槛

每个管理端页面进入工程实现前，必须先有 Stitch 交付物，且交付物要能让人肉眼和代码都追溯来源。

| 交付物 | 必须包含 | 不合格情况 |
| --- | --- | --- |
| Stitch screen | project ID、screen ID、页面标题、生成时间 | 只有口头描述，没有可追溯 screen |
| Stitch 代码或截图 | HTML/CSS 代码文件或清晰截图，能看出页面主体布局 | 只有局部组件，无法判断整页结构 |
| 页面主体颗粒 | 顶部状态区、KPI 卡、主流程、表格/明细、右侧事件流、底部状态条 | 只生成普通卡片列表，和目标图信息密度不一致 |
| 图像语言 | 工业设备、卷材、仓库、工序箭头、蓝色线稿或低饱和 3D | 使用 emoji、通用 SaaS 插画、无业务含义图标 |
| 字段映射草表 | 每个大数字对应真实 API、组合函数或明确空状态 | Stitch 静态数字直接进 Vue |

工程实现只允许把 Stitch 交付物做成可运行页面：拆组件、接路由、接真实数据、补测试。不得绕过 Stitch 重新手写整页布局。

## 目标页面颗粒度硬门槛

页面主体必须按目标图的“信息颗粒”对齐，而不是只把颜色改成蓝色。每个页面进入 Vue 实现前，先用 Stitch 生成可见的完整主体，再逐项核对下面 6 个颗粒。

| 颗粒 | 必须在 Stitch 中先出现 | Vue 落地要求 |
| --- | --- | --- |
| 顶部状态栏 | 页面名、统计周期、关键动作、更新时间、AI 入口或状态 | 套回现有 `ManageShell.vue` 页面标题和真实业务日口径 |
| 核心 KPI | 多张高密度数字卡，图标容器、主数字、单位、趋势清楚 | 每个大数字都要追到原 API、组合函数或明确空状态 |
| 主图形区 | 流程图、机列矩阵、在制料分布、能耗结构等本页核心图像 | 图像只表达真实业务链路，不新增假指标 |
| 明细区 | 紧凑表格、筛选工具、搜索、行状态、时间字段 | 保留原查询、筛选、分页、`data-testid` 和字段来源 |
| 事件区 | 异常、催报、告警、AI 摘要或缺报队列持续可见 | 事件来自现有异常/缺报/AI 接口，不用静态样例冒充 |
| 底部状态条 | 系统、数据源、同步、能耗、合同、AI 服务等状态一行展示 | 失败、加载、空数据要显示真实状态，不固定显示成功 |

如果 Stitch 稿缺少其中任何一个本页应有颗粒，先回到 Stitch 重新生成或编辑；不得在 Vue 中凭感觉手写补齐整页布局。

## Stitch 到 Vue 的强制转译顺序

每个页面都按下面顺序走，不能跳步。

1. 先在 Stitch 生成目标页面主体，不参考目标图左侧导航。

这条顺序的核心是：Stitch 负责“长什么样”，现有系统负责“数从哪来、谁能看、怎么算”。两边不能互相越界。

## 视觉设计原则

1. 全站主视觉统一为工业蓝，不再出现风格跳跃。
2. 管理端页面使用同一套 HUD 页面壳：现有导航、顶部状态栏、主内容网格、右侧事件流、底部状态条。
3. 数据密度高，但必须有清晰层级：核心 KPI 在上，流转链路在中，表格和明细在下。
4. 数字使用等宽或工业数字字体风格，保留小数显示规则，不改数据源。
5. 页面动效只做状态感：数字轻微跳动、卡片入场、扫描线、告警脉冲。不得影响读取和表单输入。
6. 表单/设置/账号/资料类页面不做“大屏炫技”，只套统一色彩、卡片、表格、按钮和输入框风格。

## Stitch 静态稿接后端路由的硬规则

10. 每个页面截图验收时同时对比目标图和 Stitch 生成稿：目标图看风格颗粒，Stitch 稿看本页具体结构。

| 5 | 保留用户操作 | 原筛选、搜索、分页、详情、按钮和 `data-testid` | 为了视觉删掉可用功能 |

小白版理解：Stitch 负责画“外观和主体骨架”，Vue 负责接“真实路线和真实数字”。Stitch 没画出来的整页主体，Vue 不能自己补；后端没有的数字，页面不能硬凑。

## 不做事项

- 不改后端算法。
- 不改数据库。
- 不删页面。
- 不合并路由。
- 不改填报端业务字段。
- 不把 Stitch 静态假数据直接写进生产页面。
- 不照搬目标图导航栏。
- 不手写绕过 Stitch 的整页前端。
- 不用“后期再调”的方式跳过截图验收。
- 不为了视觉完整添加没有真实数据来源的新业务指标。
- 不接受只有局部卡片、普通蓝色表格、普通图标库的 Stitch 稿。
- 不把目标图左侧导航、用户头像、菜单分组当成页面改造标准。
- 不在 Vue 里补画 Stitch 没有生成过的整页主体结构。

## 风险与回滚

- 最大风险：视觉重构时误删字段、误改接口、误伤 `data-testid`。
- 控制方式：每页先保留 script 逻辑，只替换 template 和 CSS；必要时只封装展示组件。
- 回滚方式：每批独立提交，任何页面异常可单独 revert 对应提交。
