## 1. 最终结论

本轮采用 **Approach B：核心体验脊柱**。

目标不是把页面“装饰得更炫”，而是让用户进入管理端后，能在 5 秒内判断：

- 今天产量、包装入库、能耗、异常、缺报是否正常。
- 哪些数据来自 MES 外部系统，哪些来自人工填报，哪些是系统算法计算。
- 哪个车间、哪台机列、哪个角色需要处理。
- 手机端填报是否能快速完成，不再出现框体溢出、字段难找、历史难查。

这次只做前端体验和视觉结构精修，默认 **不改后端算法、不改数据库、不删除接口、不改权限口径、不改业务时间口径**。如果实现中发现必须改后端字段，只允许新增兼容字段，并且旧字段继续保留。

## 2. 三视角 Review 结果

### CEO 视角

当前最大问题不是系统没有数据，而是数据被分散在多个页面里，第一眼不够像“生产指挥中枢”。用户会觉得页面很多、信息不少，但看不出主次。

本轮必须把管理端做成一条清晰的业务脊柱：

- `/manage/live` 负责实时调度，像生产现场大屏。
- `/manage/today` 负责昨日日报和经营总览，像管理层每日入口。
- `/manage/production` 负责生产分析，像追责和复盘工具。
- `/manage/fill-details`、`/manage/energy`、`/manage/alerts` 负责查明细、查能耗、查异常。
- 手机端只服务现场填报和历史确认，不承载复杂分析。

## 6. 数据流原则

前端只做展示编排，不改变业务真值来源。

```text
后端接口
  -> 页面请求层
  -> stitchManageSurface 数据整理层
  -> 页面组件
  -> 通用视觉组件
  -> 用户看到的管理端和手机端
```

每个核心数字都要保留来源感：

```text
MES 外部数据：用于参考、实时状态、包装产量、卷级线索等
人工填报数据：用于补录、对照、异常审核、内勤入库等
算法数据：用于成品率、吨耗、废料、统计汇总等
```

严禁为了页面统一，把不同来源的数据混到一个没有来源标识的卡片里。

## 7. 页面信息架构

### `/manage/live`

定位：实时生产调度墙。

首屏结构：

```text
顶部：全厂总产量、包装产量、能耗、缺报、异常、数据同步状态
中部：生产流转总览、机列矩阵、实时跳动数字
右侧：异常、催报、AI 摘要、同步事件
底部：系统状态、MES 同步、填报提交、能耗采集、更新时间
```

验收重点：

- 没数据时显示 0 或空状态，但不能页面空白。
- 有数据时数字轻量跳动，不能整页频繁刷新。
- 鼠标悬停、抽屉、事件流不能闪退。

### `/manage/today`

定位：昨日报表和每日经营总览。

首屏结构：

```text
顶部：日报核心 KPI
中部：生产流转、车间产量、包装入库、成品率、能耗
右侧：缺报、异常、AI 摘要
底部：数据同步状态和业务时间
```

验收重点：

- 包装产量、全厂入库产量、人工填报、MES 外部数据要能区分。
- 成品率、吨耗、废料等算法结果要放在合适位置。
- 缺报模块要紧凑，不能压垮页面。

### `/manage/production`

定位：生产分析和复盘。

首屏结构：

```text
顶部：产量、成品率、吨耗、合同量、异常趋势
中部：车间排行、工序对照、来源对照、趋势
右侧：关键波动、异常来源、数据质量
```

验收重点：

- 不再像普通表格页。
- 能看出 MES、填报、算法三类数据的差异。
- 趋势和排行不能因为空数据崩溃。

### 二级业务页面

`/manage/fill-details`：
做成填报链路审计台，重点看人物、机列、时间、字段、来源、异常。

`/manage/energy`：
做成能耗仪表盘，重点看采集、汇总、折算、吨耗、异常。

`/manage/alerts`：
做成异常处理中枢，重点看具体异常、严重程度、状态、责任范围。

`/manage/workshop-dashboard`：
做成车间主任看板，只显示本车间，不泄露其他车间数据。

### 手机端

`/entry`、`/entry/fill`、`/entry/history`：
做成现场填报模式，大字、少按钮、强状态、少滚动。

验收重点：

- 主操、电工、内勤能正常进入。
- 历史填报能看整日记录。
- 长车间名、长机列名、长随行卡号不溢出。

## 13. 失败模式和处理方式

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| Stitch 稿无法继续访问 | 设计依据不完整 | 使用已记录的 image2 和现有 Stitch screen id，不阻断实现 |
| 页面变美但字段错接 | 业务数字失真 | 先写 `manageStitchSurfaceMapping` 测试，锁住字段来源 |
| 实时页卡顿 | 大屏不可用 | 禁止重型光效，只做局部数字补间 |
| 手机端溢出 | 现场填报困难 | 360px 宽度验收，长文本强制处理 |
| 网络失败页面空白 | 用户误判系统坏了 | 每个核心模块必须有错误状态 |
| 车间主任看到全厂数据 | 权限风险 | 路由和接口返回都做权限可见性测试 |
| 构建 chunk 继续变大 | 页面加载慢 | 不新增重依赖，必要时懒加载二级模块 |
| 旧入口被误删 | 用户流程中断 | 本轮不删入口，只优化保留页面 |

## 14. 回滚方案

本轮不改数据库、不改后端算法，所以回滚应简单：

```text
如果只是视觉问题：回退本次前端提交
如果某个页面异常：先回退该页面改动，保留测试和通用 token
如果构建失败：不部署，停在本地分支修复
如果线上发现阻塞：回滚到上一版前端构建产物
```

回滚后必须再次打开：

- `/manage/live`

- `/entry`

确认核心入口恢复。

## 15. 分工建议

可以并行，但不能乱改同一层。

```text
Lane A：视觉 token 和通用组件
Lane B：字段映射和页面状态测试
Lane C：三大核心页面
Lane D：二级页面和手机端
Lane E：浏览器 QA、截图、评分、提交
```

推荐顺序：

```text
Phase 0 -> Phase 1 -> Phase 2 -> Phase 3 -> Phase 4 -> Phase 5 -> Phase 6
```

不能跳过 Phase 1。没有测试保护就开始改 UI，最容易把好看的页面做成错误的数据页面。

## 16. 最终完成标准

必须同时满足：

- `npm run test` 通过。
- `npm run build` 通过。
- `npm run e2e:smoke` 通过，或明确记录环境限制和替代验证。
- 核心页面浏览器实际打开通过。
- 控制台没有新增阻塞错误。
- 核心字段没有错接。
- 页面没有明显溢出。
- 五视角评分都不低于 9.5。
- 没有阻塞和高风险问题。
- 提交前有 review 记录。
