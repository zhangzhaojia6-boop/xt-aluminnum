# 2026-06-13 钉钉多模态主动汇报与多 Agent 治理实施计划

## 1. 目标

把 `鑫泰铝业 数据中枢` 建成主动汇报系统：系统继续负责真实数据、权限、算法和留痕，钉钉负责收消息、发提醒、发卡片、收图片/语音证据。

第一阶段不再只是通知，而是同时具备：

- 各车间分别主动汇报。
- 管理层收到全厂总览。
- 图片、语音、文本、卡片都能进入备案。
- 异常自动发现。
- 审核治理 Agent 拦截越权和高风险动作。
- 备案留档 Agent 记录全过程。

## 2. 当前系统可复用基础

- 钉钉基础配置已存在：`backend/app/config.py` 中已有 `DINGTALK_CORP_ID`、`DINGTALK_APP_KEY`、`DINGTALK_APP_SECRET`、`DINGTALK_AGENT_ID`、`DINGTALK_ENABLED`。
- 钉钉工作通知已存在：`backend/app/services/dingtalk_service.py` 已有 `send_work_notification`。
- 钉钉群消息已存在：`backend/app/services/dingtalk_service.py` 已有 `send_group_message`，当前依赖 `chatid`。
- 现有 Agent 基础已存在：`ReporterAgent`、`ReminderAgent` 可复用为日报汇报和催报闭环。
- 事件总线已存在：`DatabaseEventBus` 可作为主动汇报触发来源。
- AI 上下文服务已存在：`ai_context_service` 已有“先查事实、再让模型润色”的安全思路。

## 3. 不变原则

- `数据中枢` 是大脑，钉钉只是入口和出口。
- 第一阶段 AI 不直接改生产数据。
- 第二阶段才允许指定人员补产量、发布日报。
- 补产量和发布日报必须二次确认、全量留痕、可回滚。
- 图片/OCR/语音识别结果第一阶段只能作为证据，不能直接作为正式产量。
- 所有群、用户、Agent 都必须绑定权限范围。
- 未绑定权限的群不发敏感数据。
- 同一异常要限频，避免刷屏。
- 主动汇报必须少而准，不能把钉钉群变成噪音群。
- 每条主动汇报必须能追溯到数据来源和业务时间。
- 每个写动作必须能查到操作前、操作后、操作人和确认人。

## 4. Agent 设计

### 4.1 车间汇报 Agent

按车间独立运行，代码上可以是同一个 Agent 按车间参数实例化。

负责：

- 本车间产量。
- 本车间在制料。
- 本车间缺报。
- 本车间异常。
- 本车间停机。
- 本车间 MES 同步状态。

第一批车间按现有业务口径覆盖：

- 铸锭
- 铸二
- 铸三
- 热轧
- 淬火
- 精整
- 拉矫
- 园区剪切
- 新厂在线
- 园区在线
- 冷轧1650
- 冷轧1850
- 冷轧2050

### 4.2 全厂调度 Agent

负责管理层总览：

- 全厂总产量。
- 包装产量。
- 入库产量。
- 异常排行。
- 缺报排行。
- 重点停机。
- MES 同步状态。
- 当日风险事项。

### 4.3 异常检测 Agent

负责自动找问题：

- MES 有数据但填报缺失。
- 填报有数据但 MES 没匹配。
- 产量异常偏高或偏低。
- 车间长时间无产量变化。
- 能耗与产量不匹配。
- 某机列连续缺报。
- 同一指标在不同页面口径不一致。

### 4.4 审核治理 Agent

负责拦截风险：

- 这个人能不能看这条数据。
- 这个群能不能接收这条消息。
- 这条消息是否需要脱敏。
- 这个动作是否必须二次确认。
- 这个异常是否要升级到管理层。

### 4.5 备案留档 Agent

负责记录证据：

- 谁触发。
- 发到哪个群。
- 用了哪些数据。
- AI 输出了什么。
- 谁确认了。
- 是否执行动作。
- 图片、语音、附件原始证据。
- 失败原因和重试记录。

### 4.6 消息节流 Agent

负责防止刷屏：

- 同一异常 30 分钟内只推一次。
- 红色异常立即推。
- 黄色异常合并到整点汇报。
- 绿色状态只进入日报或管理端，不主动打扰群。
- 夜间只推红色异常和日报节点消息。

### 4.7 指定操作 Agent

第二阶段启用。

负责：

- 识别指定人员。
- 校验指定群。
- 生成补产量预览。
- 生成日报发布预览。
- 等待二次确认。
- 执行后留痕。
- 失败时自动回退到人工处理。

## 5. 多模态范围

### 5.1 文本

用于：

- 主动汇报。
- 群内问答。
- 异常说明。
- 审核意见。
- 日报摘要。

### 5.2 图片

用于：

- 一体机截图。
- 随行卡照片。
- 设备现场照片。
- 异常现场照片。
- 生产记录截图。

处理方式：

- 先保存原图。
- 再做 OCR。
- OCR 结果标记为参考证据。
- 人工确认前不进入正式产量。

### 5.3 语音

用于：

- 现场异常说明。
- 停机原因补充。
- 班组交接说明。

处理方式：

- 语音转文字。
- 原语音和文字都备案。
- 第一阶段不允许语音直接触发写数据。

### 5.4 卡片

用于：

- 查看详情。
- 确认收到。
- 转人工核查。
- 查看日报预览。
- 第二阶段再开放补产量、发布日报。

## 6. 后端实施阶段

### 阶段 0：只读核对

目标：不改业务，只确认现有能力。

动作：

- 核对钉钉配置项。
- 核对钉钉工作通知。
- 核对钉钉群消息。
- 核对 ReporterAgent 和 ReminderAgent。
- 核对事件总线。
- 核对 AI 上下文服务。

验收：

- 明确哪些能力可复用。
- 明确哪些能力需要新增。
- 不影响线上业务。

### 阶段 1：通讯底座

新增表和服务：

- `agent_profiles`：Agent 配置。
- `communication_channels`：钉钉群、用户、机器人通道。
- `agent_channel_bindings`：Agent 和群绑定。
- `agent_events`：事件池。
- `agent_outbox`：待发送消息。
- `agent_runs`：Agent 运行记录。
- `external_message_logs`：钉钉发送结果。
- `multimodal_evidence`：图片、语音、附件证据。
- `agent_operation_approvals`：补产量、发布日报等二次确认记录。
- `agent_rate_limits`：异常限频和消息节流记录。

验收：

- 可以 dry-run 生成消息但不发钉钉。
- 可以看到消息准备发给谁。
- 失败不会丢，能重试。
- 未绑定群不允许发送生产数据。
- 每条消息都带业务时间、数据来源和 trace id。

### 阶段 2：主动汇报

实现：

- 车间汇报 Agent。
- 全厂调度 Agent。
- 异常检测 Agent。
- 审核治理 Agent。
- 备案留档 Agent。
- 消息节流 Agent。

触发方式：

- 定时触发：早会、整点、交班、日报。
- 事件触发：缺报、停机、异常、MES 同步失败。
- 人工触发：管理员手动运行某个 Agent。

验收：

- 一个管理钉钉群收到全厂总览。
- 一个试点车间群收到本车间汇报。
- 没权限的群收不到敏感数据。
- 同一异常不会重复刷屏。
- 主动汇报内容能在管理端查到来源。
- 群里收到的消息不超过预设频率。
- 异常消息能区分待核查、已确认、已关闭。

### 阶段 3：多模态接入

实现：

- 钉钉图片消息入库。
- 钉钉语音消息入库。
- OCR 结果入库。
- 语音转文字结果入库。
- 证据和异常、日报、补录申请关联。
- 图片和语音的识别结果分为“机器识别”和“人工确认”两类。
- 未人工确认的识别结果不进入正式指标。

验收：

- 图片能保存、能查看、能 OCR。
- 语音能保存、能转文字。
- 识别结果不直接改正式数据。
- 原始文件、识别文字、人工确认结果都能追溯。

### 阶段 4：指定人员操作

只开放给指定人员：

- 补产量。
- 发布日报。

流程：

1. 指定人员在钉钉发起。
2. 系统识别身份。
3. 系统校验白名单。
4. 系统生成操作预览。
5. 用户二次确认。
6. 后端执行。
7. 写入日志。
8. 推送结果。

限制：

- 只允许在已绑定的管理群或授权车间群发起。
- 只允许白名单人员发起。
- 补产量只写入人工补录/纠偏记录，不修改 MES 原始数据。
- 发布日报必须先生成预览。
- 预览和最终发布内容必须一一对应。
- 任何失败都不能影响原有日报和填报流程。

验收：

- 普通人不能补产量。
- 普通人不能发布日报。
- 指定人员操作有完整记录。
- 发布日报前必须有预览。
- 未确认前不能执行。
- 执行后能从管理端查到完整证据链。

### 阶段 5：RAG 知识库

资料范围：

- 日报口径。
- MES 字段说明。
- 车间规则。
- 异常处理流程。
- 设备说明。
- 填报说明。
- 权限规则。

验收：

- Agent 能解释指标口径。
- 回答带资料来源。
- 不用 RAG 编造实时数据。

## 7. 前端管理页面

新增或改造：

- `/manage/agents`：Agent 列表、启停、最近运行、异常数。
- `/manage/channels`：钉钉群、人员、机器人、绑定范围。
- `/manage/agent-events`：事件池和处理状态。
- `/manage/agent-outbox`：消息发送队列和失败重试。
- `/manage/evidence`：图片、语音、附件证据。
- `/manage/rag`：知识库文档、切片、启停。
- `/manage/agent-approvals`：补产量、发布日报、异常确认等待审批事项。

原则：

- 页面全中文。
- 不加无意义说明文字。
- 重点显示“谁、什么事、发到哪里、成功没有、能不能回滚”。
- 每个列表默认只显示最重要的列。
- 移动端只保留待办、确认、查看证据三类动作。
- 管理端必须能一眼看出消息是否真的发出去了。

## 8. 钉钉后台需要你做什么

### 8.1 准备管理员权限

你需要一个钉钉企业管理员账号，能进入：

- 钉钉管理后台。
- 钉钉开放平台。
- 企业内部应用管理。
- 群机器人管理。

### 8.2 创建企业内部应用

建议应用名：

`鑫泰数据中枢AI助手`

用途：

- 获取企业身份。
- 发个人工作通知。
- 后续支持 H5 免登。
- 支持指定人员补产量、发布日报时做身份确认。

你需要记录这些参数：

- `CorpId`
- `AppKey`
- `AppSecret`
- `AgentId`

这些值不要发到群里，不要写进文档，不要截图公开。只放到服务器环境变量里。

### 8.3 给应用开权限

第一阶段建议开：

- 读取通讯录基础信息。
- 获取用户 userid。
- 发送工作通知。
- 机器人收消息。
- 卡片消息回调。
- 文件或图片消息读取。

如果钉钉后台权限名称略有差异，以钉钉实际页面为准。

### 8.4 配置机器人/Stream

第一阶段建议用钉钉机器人或 Stream 模式接收群消息。

需要配置：

- 机器人名称：`数据中枢AI助手`
- 安全设置：优先使用加签或企业应用身份，不建议只用关键词。
- 回调地址：上线后由系统提供。
- 消息范围：只允许指定测试群和正式生产群。

## 10. 上线顺序

1. 本地 dry-run。
2. 测试钉钉群。
3. 一个试点车间群。
4. 管理总控群。
5. 全部车间群。
6. 第二阶段开放指定人员补产量和发布日报。

## 11. 回滚方案

- 每个 Agent 都有启停开关。
- 每个群都能单独解绑。
- 钉钉发送失败不影响主系统。
- 多模态识别失败只影响证据，不影响正式数据。
- 第二阶段写动作有日志和回滚记录。
- 出现误推送时，先停 Agent，再查 outbox 和 run log。

## 12. 第一阶段完成标准

- 管理群能收到全厂主动汇报。
- 试点车间群能收到本车间主动汇报。
- 异常检测能生成待核查事项。
- 审核治理能拦截越权消息。
- 图片和语音能作为证据留档。
- 消息失败能重试。
- 所有 Agent 运行都有日志。
- 不影响 `/entry`、`/manage`、日报、MES 同步、现有填报流程。
- 群消息、管理端记录、数据库日志三处能对上。
- 多模态证据只作为参考，不进入正式数据。
- 审核治理 Agent 能拦住未授权群和未授权人员。

## 13. gstack 五视角复审

### 13.1 CEO 视角

评分：9.7。

判断：

- 方案直接解决“老板和管理层不能及时知道现场情况”的问题。
- 主动汇报、异常检测、催办闭环比单纯聊天机器人更有业务价值。
- 第一阶段先做管理群和试点车间群，风险可控，见效快。

需要坚持：

- 不追求花哨聊天，先追求异常早发现、日报少人工、责任能闭环。
- 每条推送都要短，管理层一眼看懂。

### 13.2 工程师视角

评分：9.6。

判断：

- 复用现有钉钉服务、ReporterAgent、ReminderAgent、事件总线，工程风险低于重写。
- 新增 outbox、run log、approval、evidence 表是必要复杂度，不是无意义扩张。
- 最大风险是钉钉接收消息和多模态文件处理，需要先 dry-run，再试点。

需要坚持：

- 第一阶段只加旁路，不改核心生产统计。
- 每个阶段都要有测试和开关。
- 不直接让 Agent 查散乱 SQL，优先走已有后端服务。

### 13.3 设计师视角

评分：9.6。

判断：

- 管理端不能做成复杂机器人后台，要做成“消息、事件、证据、审批”四个清楚区域。
- 钉钉卡片不能长篇大论，要像生产告警牌。
- 车间群消息要能马上看出状态、影响、责任、动作。

需要坚持：

- 所有页面全中文。
- 页面少解释，重状态和操作。
- 移动端只保留确认、查看、转人工。

### 13.4 安全审查视角

评分：9.7。

判断：

### 13.5 真实用户视角

评分：9.8。

需要坚持：

- 群消息不要刷屏。
- 操作步骤不能超过“发起、预览、确认”三步。
- 出错时要告诉用户“为什么不允许”和“去哪里处理”。

## 14. 五视角优化后的执行顺序

第一步：只读核对和 dry-run。

第二步：通讯底座、outbox、群绑定、权限绑定。

第三步：管理群和一个试点车间群主动汇报。

第四步：异常检测、审核治理、备案留档。

第五步：图片和语音证据接入。

第六步：管理端四个页面闭环：Agent、通道、事件、证据。

第七步：指定人员补产量和发布日报。

第八步：RAG 知识库解释口径。

## 15. 不允许进入下一阶段的情况

- 钉钉测试群收不到 dry-run 消息。
- 群和车间没有绑定清楚。
- 未授权人员能看到其他车间数据。
- 同一异常重复刷屏。
- 图片或语音识别结果被当成正式数据。
- 补产量绕过二次确认。
- 日报发布没有预览。
- 发送失败没有日志。
