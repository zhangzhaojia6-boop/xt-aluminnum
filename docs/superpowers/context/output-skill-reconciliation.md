# 输出skill 数据对齐说明

## 1. 目标

本文件专门告诉 Codex 如何把云端数据库里的“平台映射汇总算法结果”和 `D:\输出skill` 里的目标数据做高匹配对齐。目标不是硬改数据，而是找出字段、单位、班次、日期、车间、机台、工序、卷号、合同、辅材、能耗、质量、停机等口径差异，然后生成可解释的匹配规则。最终目标是同口径字段匹配度尽量达到 95% 以上；达不到时必须说明差异来自哪张表、哪个字段、哪个业务口径、哪个计算公式或哪个数据源缺失。

## 2. 数据源

参考源：`D:\输出skill`。Codex 执行时如果运行环境不能直接访问 Windows 路径，应要求将该目录只读挂载为仓库内 `reference/output-skill/`，或者通过云端文件、MCP、临时同步目录读取。该目录里的文件只能作为参考和对齐基准，不要把原始敏感数据提交到 Git。若需要测试样例，只能抽取脱敏后的少量 fixture，放到 `backend/tests/fixtures/output_skill_mapping_sample.*`。

系统源：云端数据库。需要读取平台映射汇总算法相关表、生产汇总表、移动填报表、MES 同步表、车间/班组/机台/工序主数据、辅材表、能耗表、质量表、停机/维修表、日报表、映射配置表、别名映射表、审计表。先只读分析，不能一上来改真实生产数据。

## 3. 第一轮必须输出的审计文档

新增或更新 `docs/audits/output-skill-data-mapping-baseline.md`，内容包括：

1. 读取了哪些 `D:\输出skill` 文件。
2. 读取了哪些云端数据库表。
3. 每个目标字段对应系统哪个字段。
4. 字段是否有别名、单位换算、时间口径、精度口径。
5. 哪些字段完全匹配。
6. 哪些字段差异可解释。
7. 哪些字段系统缺数据。
8. 哪些字段输出skill缺数据。
9. 哪些字段疑似算法口径不同。
10. 推荐修正规则和测试 fixture 位置。

## 4. 字段映射范围

优先识别以下字段：

车间字段：车间名称、车间编码、工段、工序、生产线、机台、机列、班组、班次、人员、负责人。

时间字段：自然日、生产日、班次日期、开班时间、交班时间、填报时间、MES 同步时间、日报日期、统计开始时间、统计结束时间。

卷材字段：卷号、随行卡号、批号、合同号、客户、牌号、规格、厚度、宽度、长度、上机卷、下机卷、在制卷、成品卷、废料卷、返工卷。

产量字段：上机重量、下机重量、投入重量、产出重量、包装重量、入库重量、成品重量、废料重量、班次产量、日累计产量、车间累计产量、全厂累计产量。

质量字段：成材率、良品率、废品率、返工率、厚度偏差、表面缺陷、质量异常数、质量门禁状态、质量原因、处理人、处理状态。

辅材字段：辅材名称、辅材编码、领用数量、消耗数量、库存数量、单位、单吨消耗、定额、超耗率、领用人、领用班次、对应车间/机台/工序。

能耗字段：电量、气量、水量、蒸汽、单位吨耗、车间能耗、机台能耗、峰谷平、电费、气费、统计时间。

停机字段：停机开始、停机结束、停机时长、停机机台、停机原因、维修人、预计恢复时间、实际恢复时间、停机等级、是否重复停机、是否超时。

成本字段：铝价、加工费、能耗成本、辅材成本、人工成本、维修成本、吨成本、利润快照、合同吨数、收入估算。

## 5. 口径差异优先检查

先检查单位：kg 和吨必须统一。系统中部分数据可能按 kg 存，报表按吨展示；输出skill 可能已经换算成吨。统一规则是：重量内部可保留原单位，但对比时必须声明单位，按同一单位算匹配率。

再检查小数精度：金额保留 2 位，吨数通常保留 2 或 3 位，成材率保留 2 位百分比。对比时允许小范围误差：重量默认容差 0.01 吨或 0.1%，金额默认容差 0.01 元或 0.1%，百分比默认容差 0.01 个百分点。实际容差要在审计文档里写清。

再检查日期：自然日和生产日不能混用。夜班跨日时，生产日应按业务规则归属，不一定等于自然日。必须查系统里的班次配置、业务日期函数和报表生成逻辑。

再检查班次：白班、夜班、早班、中班、晚班、甲班、乙班等可能有别名，必须先做班次别名表，不要直接按文本硬比。

再检查车间和机台别名：输出skill 里的“冷轧”“轧制”“轧机”“1#机”“一号机”“M01”可能指系统同一个标准对象。必须先建立标准名映射，再算匹配率。

再检查数据状态：系统可能有 draft、submitted、reviewed、confirmed、published、blocked 等状态。输出skill 可能只统计已确认或已发布数据。对比时必须区分“原始填报”“已确认数据”“已发布日报”“算法最终数”。

再检查来源：人工填报、MES、算法推算、补录、Excel 导入不能混成一个来源。对比时必须标注来源。

## 6. 匹配率算法

字段级匹配率：同一字段在同一统计维度下，匹配条数 / 可比条数。可比条数不包括两边都为空且业务上无意义的行。

记录级匹配率：同一日期、车间、班次、机台、卷号或合同号下，关键字段全部在容差内才算匹配。

汇总级匹配率：按日期、车间、班次汇总后的产量、辅材、能耗、停机等指标与输出skill 对比，在容差内算匹配。

综合匹配率：优先按业务重要性加权，建议权重为产量 30%、成材率 15%、辅材 15%、能耗 15%、停机 10%、质量 10%、其他 5%。如果某类数据当前没有接入，要从总分中单独说明，不要假装匹配。

8. 后端接口建议

新增或复用以下接口：

GET /api/v1/mapping-reconciliation/sources：列出可读取的输出skill 文件和系统数据表。

POST /api/v1/mapping-reconciliation/run：传入日期、车间、班次、文件范围，执行对比。

GET /api/v1/mapping-reconciliation/runs/{id}：查看一次对比结果。

GET /api/v1/mapping-reconciliation/runs/{id}/differences：查看差异明细。

POST /api/v1/mapping-reconciliation/rules/propose：根据差异自动生成推荐口径规则。

POST /api/v1/mapping-reconciliation/rules/apply-dry-run：只做试算，不直接改生产配置。

9. 前端页面要求

新增或完善 /manage/mapping-reconciliation。页面需要有四块：数据源选择、匹配率总览、差异明细表、口径规则建议。视觉必须是中国风工业大气，不能有 AI 味。重点看得清楚：今天匹配率多少、哪类数据差异最大、差异来自单位还是班次还是别名、下一步应该改哪个配置。

页面要支持按日期、车间、班次、机台、字段类型筛选。差异表要显示“输出skill 值”“系统值”“差异”“可能原因”“建议规则”“是否可自动修正”。自动修正默认只 dry-run，不直接改真实生产口径。

10. 测试要求

后端测试至少覆盖：

kg 与吨换算。
生产日跨自然日。
班次别名匹配。
车间/机台别名匹配。
小数容差。
系统多一行。
输出skill 多一行。
字段缺失。
汇总匹配率计算。
dry-run 规则建议不改真实数据。

前端测试至少覆盖页面能渲染、筛选条件能改变请求、匹配率卡片显示、差异表显示、规则 dry-run 按钮可用。

11. 禁止事项

禁止为了提高匹配率直接改生产数据库原始数据。禁止把输出skill 原始敏感数据提交到 Git。禁止在最终报告里打印客户、员工、密钥、数据库连接。禁止只给“匹配失败”结论而不解释字段和口径。禁止让大模型凭感觉判断匹配，要用确定性代码算。

12. 验收标准

同口径字段尽量 95%+。如果没有达到，要给出清楚的分类：数据源缺失、单位差异、日期差异、班次差异、别名差异、算法差异、状态过滤差异、历史补录差异、无法判断。最终报告必须带匹配率、关键差异、推荐规则、测试结果、浏览器页面验证结果。
