# 2026-06-14 Agent 通讯、RAG、钉钉、前端重构业务方向

## 1. 总结论

本系统目标能做。正确做法不是把 AI 真正装进钉钉机器人或微信机器人里，而是让 `xt-aluminnum / aluminum-bypass` 后端继续做“大脑和账本”，钉钉、企业微信、微信只做“嘴巴、耳朵和广播室”。先做钉钉，再做企业微信。个人微信只建议做试验入口，不建议作为正式生产核心，因为普通个人微信群没有稳定官方实时读取接口，靠 RPA 或扫码机器人方案可以测试，但不适合承载工厂关键通知。

系统现有方向是“独立填报端 `/entry` + 管理审阅端 `/manage` + Agent 自动校验汇总 + 浏览器/钉钉试跑优先 + 历史系统端口兼容”。现有系统已经有手机填报、管理端、钉钉 H5、日报、催报、实时流、部分 Agent、AI context、企业微信配置基础，所以最省力路线是保留现有系统，补“通讯中台、事件总线、RAG 知识库、消息适配器和 Agent 编排层”，不是重写系统。

## 2. 目标架构

系统数据库、MES、能源表、维修表、辅材表、质量表、手机填报表是事实仓库。Agent 是值班员。钉钉群和企业微信群是广播室。RAG 是资料室。大模型只是把事实说成人能看懂的话的总结员。

数据从现场进入系统，系统产生事件，事件交给不同 Agent 判断。Agent 只能拿它有权限看的数据和知识库资料。Agent 生成短消息、卡片、建议动作，再通过钉钉机器人、钉钉工作通知、企业微信机器人或管理端通知发出去。

## 3. RAG 和微调的关系

先做 RAG，不要先做微调。RAG 像开卷考试，适合 SOP、设备说明、工艺规则、历史日报、异常处理手册、字段解释、维修流程、辅材定额、质量标准这类会变的知识。微调像训练说话习惯，适合训练回复格式、企业语气、分类规则，不适合记实时产量、停机和消耗，因为实时数据天天变，必须查数据库。

第一阶段只做 RAG 和工具调用。第二阶段等积累一个月真实问答、人工修正、最终正确答案后，再做小规模微调。微调数据必须有 evidence，不允许用错数训练。

## 4. 开源参考

可参考 Dify、RAGFlow、LangBot、CowAgent、Wechaty，但不能把业务系统整体迁过去。Dify 适合借鉴 AI workflow、RAG pipeline、Agent、模型管理、观测和 API。RAGFlow 适合借鉴文档入库、复杂文档解析、切块、引用和减少幻觉。LangBot 和 CowAgent 适合借鉴“一个 Agent 核心，多种聊天入口”的多平台通道设计。Wechaty 只适合作为个人微信测试参考，不作为正式生产主通道。

核心原则：业务数据、权限、审计、日报、车间隔离留在 `xt-aluminnum`。外部聊天平台只调用统一接口 `/api/v1/agent/command`。

## 5. Agent 名单

第一批 Agent：

全厂总控 Agent：负责全厂总览、重大异常、日报摘要。

车间状态检测专员 Agent：每个车间一个，负责开机、停机、维修、异常、产量、辅材、填报状态。

修停机 Agent：盯设备状态、停机原因、维修人、预计恢复时间、停机超时、重复停机。

上下机产量 Agent：盯上机重量、下机重量、班次产量、投入产出差、成材率。

辅材消耗 Agent：盯油、气、包装、刀具、轧辊、纸套筒、辅材库存、吨耗、超定额。

质量 Agent：盯废品、返修、厚度偏差、表面缺陷、质量门禁、缺陷率。

能源成本 Agent：盯电、气、水、单吨能耗、成本快照。

库存 Agent：盯原料、半成品、成品、入库、包装。

安全 Agent：盯异常高温、烟感、门禁、人员违规。

管理层日报秘书 Agent：每天发老板看得懂的日报和经营摘要。

催报 Agent：催未填、迟填、退回未改的数据。

微信群状态监测 Agent：只允许做合规试验，不偷读、不绕过权限、不接关键生产写操作。

## 6. 数据表建议

新增或复用以下表：

`agent_profiles`：Agent 名称、角色、描述、管辖车间、管辖班组、启停状态、频率、安静时间、严重等级阈值。

`communication_channels`：钉钉群、钉钉工作通知、企业微信群、内部通知、微信试验入口、webhook、chat_id、密钥引用、dry-run 状态。

`agent_channel_bindings`：哪个 Agent 绑定哪个群、什么等级发到哪里、是否 @负责人。

`agent_event_rules`：触发规则，比如停机超过 10 分钟、产量低于计划 80%、辅材超过定额 110%。

`agent_events`：现场事件，比如停机、恢复、提交、催报、日报发布、质量异常、辅材超耗。

`agent_runs`：每次 Agent 为什么运行、查了哪些事实、查了哪些 RAG、做了什么判断。

`agent_outbox`：所有外发消息先进入 outbox，再投递到钉钉或企业微信，支持重试和 dead-letter。

`chat_inbox`：外部群消息入口，保存群、发送人、文本、提到的 Agent、trace_id。

`external_message_logs`：钉钉、企微真实返回结果和失败原因。

`rag_documents`：上传文档元数据。

`rag_chunks`：文档切片。

`rag_query_logs`：RAG 查询记录。

`prompt_versions`：提示词版本。

`agent_feedback`：人工点赞、纠错、误报记录。

## 7. 现有系统复用原则

保留现有 AggregatorAgent，它已经能按日期汇总已确认生产数据，生成产量、上报率、成材率、出勤、能耗、车间摘要和异常摘要。后续只是把它能力拆给日报 Agent 和车间实时 Agent，不推倒。

保留现有 ReminderAgent，它已经能检查未报/迟报班次，前三次催报，超过次数升级给管理员。后续只是把催报通道扩展到群内提醒、负责人私聊、管理员升级群。

保留现有 ReporterAgent，它已经能查 published 日报，判断质量门禁，生成日报消息并推给 admin/manager。后续要补群消息、按车间发不同群、失败重试和消息幂等。

保留现有 DingTalkService、DingTalk H5、钉钉用户绑定字段、企业微信 WeComGroupBotPublisher、RealtimeEventBus、WorkflowDispatcher、AI Context Service。

## 8. 钉钉路线

钉钉先做两条线：

第一条是群机器人或 DingTalk Stream，用来把车间状态发到群里，也支持群里 @Agent 问问题。

第二条是企业内部应用工作通知和 H5 免登，用来给个人催报，让人点卡片进 `/entry` 或 `/manage`。

建议先建一个“鑫泰生产 AI 助手”总应用，然后在系统里配置多个 Agent 身份。不要一开始在钉钉后台建很多不可控的散乱机器人。系统内部负责区分“全厂总控、车间状态、修停机、辅材、质量、日报”等角色。

钉钉群建议：

`鑫泰生产总控群`：老板、厂长、生产、设备、质量、仓库负责人。

`冷轧车间状态群`、`铸轧车间状态群`、`箔轧车间状态群`：按车间建。

`修停机响应群`：设备、维修、车间负责人。

`辅材与库存群`：仓库、采购、车间。

`质量异常闭环群`：质检、车间、管理人员。

每个 Agent 只发自己该发的群，避免刷屏。

## 9. 企业微信和个人微信路线

企业微信可以正式生产使用。企业微信群机器人适合通知，企业微信自建应用适合收消息、做身份、发应用消息。仓库已有企业微信相关配置位，应复用。

普通个人微信只做试验，不做生产主通道。如果必须试验，单独部署微信监听代理，用非核心微信号加入白名单群，只监听授权群，只保存必要字段，不保存私人聊天原文，收到“状态、产量、停机、辅材”等关键词后转发给 `/api/v1/agent/command`，Agent 回答后再发回群。不要让微信代理直接改生产数据。

## 10. 消息等级和模板

消息等级：

绿色：正常，只记录或整点摘要发。

黄色：轻微异常，发车间群。

橙色：影响生产，发车间群并 @负责人。

红色：重大异常，发总控群、负责人、管理员，并要求确认。

同一异常 30 分钟内只提醒一次。夜间只发红色。群里连续追问要限流。

固定模板：

`【范围｜时间】状态：绿/黄/橙/红；结论；关键数字；原因；建议动作；数据来源；可回复命令`

例子：

`【冷轧车间｜14:30】状态：橙；3号机停机 32 分钟，本班预计少产 1.8 吨；原因：换辊未完成；建议设备员 15 分钟内反馈恢复时间；来源：停机记录 + 班次填报；回复：3号机详情 / 今日产量 / 辅材明细。`

## 11. RAG 知识库范围

第一批资料：

车间工艺流程、设备台账、设备说明书、维修 SOP、停机原因分类表、辅材定额表、质量缺陷说明、成材率规则、MES 字段映射、日报样例、领导常问问题、岗位填报说明、异常闭环流程、钉钉群使用规则、权限规则、主数据说明、接口说明、部署说明。

资料入库前要清洗。每份文档要有 source_name、version、workshop、machine_code、owner、effective_date、permission_scope。没有来源的文档不允许进入正式知识库。

切片规则：普通中文文档按 500 到 800 字切块，前后重叠 80 到 120 字；表格按“表名 + 字段 + 解释 + 示例”切；日报按“日期 + 车间 + 指标 + 异常 + 总结”切；维修记录按“机台 + 故障 + 原因 + 处理方法 + 结果”切。

RAG 回答必须带来源。没有数据就说“数据不足，系统未收到最新数据”，不能编。

## 12. Agent 查询流程

外部群消息或系统事件进入后，统一流程：

1. 识别人：钉钉 user_id / union_id / 企业微信 user_id / 内部用户。
2. 识别群：chat_id / webhook / channel_id。
3. 校验权限：群和用户能看哪个车间、班组、字段。
4. 识别意图：车间状态、停机、产量、辅材、质量、能耗、日报、催报。
5. 查实时事实：优先查系统已有实时接口和业务服务，不直接拼杂乱 SQL。
6. 查 RAG：按车间、设备、意图检索 SOP 和字段说明。
7. 组织短回答：固定模板，带数据时间和来源。
8. 写审计：chat_inbox、agent_runs、agent_outbox、external_message_logs。
9. 外发：钉钉/企业微信/内部通知。
10. 人工反馈：支持确认、纠错、升级。

## 13. 前端重构方向

前端要中国风工业大气，不要 AI 味。不要机器人头像、霓虹科技球、英文大模型营销词、花哨渐变海报。采用深墨黑、钢铁灰、青铜金、暗红状态灯、玉白文字、细边框、压暗纹理、工厂驾驶舱大数字、稳重表格、厚重卡片、清晰筛选器、抽屉、确认弹窗。

新增或完善页面：

`/manage/admin/agents`：通讯治理台，包含 Agent 列表、启停、车间范围、绑定群、触发规则、最近运行、发件箱、失败重试。

`/manage/rag`：文本附件知识库，支持上传、列表、详情、切片预览、删除、测试问答。

`/manage/channels`：外部通讯配置，支持钉钉群、钉钉工作通知、企业微信群、内部通知、dry-run 和真实发送测试。

`/manage/mapping-reconciliation`：输出skill 对齐，展示匹配率、差异表、口径规则、修正建议。

`/manage/ai-assistant`：接入 RAG 查询结果和证据来源。

手机端 `/entry` 保持现场工人易用，大按钮、大输入框、少字、单手可操作，不要为了视觉破坏填报效率。

## 14. 业务闭环

完整链路：

现场员工在 `/entry` 填报，MES/能耗/辅材/质量数据同步进系统，平台映射汇总算法计算，系统与 `D:\输出skill` 对齐，异常被识别，Agent 判断状态，钉钉群播报，群里可追问，RAG 查制度解释，管理员处理，日报生成，管理层查看，审计留痕。

每条链路都要能回答：

数据从哪来？
怎么算的？
谁能看？
发给谁？
谁确认？
哪里能追溯？
和输出skill 差多少？
差异原因是什么？

## 15. 验收标准

一个试点车间先跑通。验收标准：

数据不丢。
消息不乱发。
权限不越界。
同一异常不重复刷屏。
关键异常 5 分钟内进群。
催报能闭环。
日报数字和系统一致。
RAG 回答能给来源。
输出skill 同口径字段匹配度尽量 95%+。
人工能一键纠错。
前端页面能打开，接口没坏，构建通过。
真实钉钉消息能发到测试群。
浏览器验证有证据。
